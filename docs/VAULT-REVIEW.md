# مراجعة أمنية مستقلة لدمج خزنة التشفير E2EE في موقع PGOS

**المراجع:** مستقل عن مؤلف الدمج · **التاريخ:** 2026-11-22 ~05:20 EET · **النطاق المراجَع:** كوميت الدمج `1fdd4e5` + شجرة العمل كما وُجدت أثناء المراجعة · **المصدر المقارَن:** `/tmp/pgos-app-check` (نسخة `pgos-app`، لم تُلمس)

## الحكم: ✅ جاهز للنشر المشفّر — بتحفّظات إجرائية (لا عيب يمنع النشر)

الخزنة نفسها سليمة تشفيريًا والدمج صحيح، وكل فحوص الرفض والعبث تعمل بتشغيل فعلي. التحفظات كلها **إجرائية** وتتعلق بخطوة النشر لا بالكود: ملف البيانات الواضحة **موجود افتراضيًا في `dist/`** بجانب المشفّر، والحماية الوحيدة منه خطوة حذف يدوية/سكربت ظهر أثناء المراجعة ولم يُلتقَط في كوميت بعد. بشرط الالتزام بخطوة النشر المُثبتة (تحفظ R1 أدناه) النشر المشفر آمن.

## ١) سلامة التشفير — مفحوصة من الكود مباشرة

| الفحص | النتيجة |
|---|---|
| النقل حرفي؟ | `diff` بين `src/lib/vault.mjs` والأصل: **لا فرق إطلاقًا**؛ `docs/VAULT-FORMAT.md` أيضًا مطابقة بايتًا. |
| DEK عشوائي لكل لقطة؟ | نعم — `random(32)` من `crypto.getRandomValues` عند كل `wrapSnapshot`. |
| IV عشوائي؟ | نعم — `random(12)` منفصل للحمولة ولكل تغليف جهاز. |
| HKDF بنفس المعاملات في التشفير والفك؟ | نعم — قرأت موقعي الاستدعاء: التغليف `deriveKek(eph_priv, device_pub, ephRaw)` والفك `deriveKek(device_priv, eph_pub, wrap.eph)`؛ `salt` = المفتاح العمومي المؤقت الخام و`info = "pgos/v1/dek-wrap"` في الحالتين، والسر المشترك ECDH متماثل بالبناء. |
| GCM يرفض العبث؟ | نعم — قلب بايت في الحمولة يُرفض `DECRYPT_FAIL` (مثبت بالتشغيل، انظر §٥). |
| بصمة الجهاز في `devices.json`؟ | أعدت حسابها من المفتاح العمومي: **مطابقة للمخزنة** (`8058-b17b-c2ab-1c7d-d906`) — فالتغليف يطابق الجهاز فعلًا. |
| AAD؟ | لا يوجد AAD يربط التغليف بالحزمة. عمليًا بلا أثر: تغليف مُنقَل لحزمة أخرى يفك DEK خاطئًا فيرفض GCM الحمولة. ملاحظة فقط، ليست ثغرة. |

البناء قياسي وسليم (ECDH مؤقت + HKDF + AES-256-GCM، DEK جديد لكل لقطة) ويطابق `VAULT-FORMAT.md` حرفيًا. لم أجرِ تدقيقًا تشفيريًا رسميًا للتصميم الأصلي — هذه مراجعة دمج لا تدقيق بروتوكول.

## ٢) التسربات — فحص `dist/` بنفسي

شغّلت بنفسي: `npm run data` ← `npm run data:encrypt` ← `npm run build` (بيانات حقيقية، 202,802 بايت → لقطة مشفرة 270,872 بايت):

| المكان | النتيجة |
|---|---|
| `dist/data/snapshot.enc.json` | **0 ظهور** لأي من `3A-316` / `L-0017` / `TOTO-001` / `records` / `ledger` — نص مشفر فقط. |
| `dist/data/site-data.json` | **موجود بوضوح كامل** (48 ضربة للعلامات، منها `3A-316` 15 مرة) — **هذا هو مسار التسرب الوحيد والأخطر**: أي رفع لـ`dist/` كما هو ينشر البيانات الواضحة بجانب المشفرة. |
| حزمة JS المبنية | نظيفة في شجرة العمل الحالية (0 علامات). تنبيه دقيق: في **الحالة المُلتقَطة** (كوميت `1fdd4e5`) كانت صفحتا Validation/Adoption تحتويان حرفيًا `WO-TOTO-001` / `DEC-TOTO-001` في نص الواجهة، فظهرتا مرتين في الحزمة المبنية من تلك الحالة — تعديلات غير مُلتقَطة أثناء المراجعة استبدلتهما بإشارات عامة فاختفتا. أي أن فحص العلامات على `dist` يفشل على الحالة المُلتقَطة وينجح على شجرة العمل الحالية. |
| `vercel.json` | إعادة كتابة SPA تستثني `data/` و`assets/` — أي أن `/data/site-data.json` يُخدَم كملف حقيقي، ولا يخفي غياب `snapshot.enc.json` صفحة HTML بـ200. وفحص الشكل في `unlock.ts` (`v===1` + `payload.ct` + `wraps`) حماية إضافية صحيحة. |
| كاش/سجلات | لا `localStorage`/`sessionStorage` في مسار الخزنة إطلاقًا (بحث نصي)؛ البيانات المفكوكة تعيش في كاش ذاكرة `data.ts` فقط؛ جلب الحزمة بـ`cache: 'no-store'`. |

**الخلاصة:** البوابة تعمل، لكنها تعتمد كليًا على خطوة النشر. السكربت `tools/build_encrypted.mjs` (يبني، يحذف الواضح، ويفشل عند أي علامة) هو الضمان الصحيح — لكنه **ظهر أثناء المراجعة غير مُلتقَط** (مع سكربت `build:encrypted` في `package.json` غير مُلتقَط أيضًا). شغّلته بنفسي فنجح: `ENCRYPTED BUILD OK`.

## ٣) تدفق التفعيل

- **كود التفعيل عمومي فعلًا:** `ActivationCodeBox` يعرض `info.pub` فقط — المفتاح العمومي الخام base64url + البصمة. لا أثر لأي مادة سرية في الشاشة.
- **المفتاح الخاص غير قابل للاستخراج فعلًا:** يُولّد بـ`generateDeviceKeyPair(false)` ويُحفظ في IndexedDB كما هو (مفاتيح WebCrypto غير القابلة للاستخراج تبقى كذلك عبر التخزين المنظم).
- **استيراد JWK:** المفتاح الخاص يُستورد `extractable: false` — سليم. ثغرتان صغيرتان موثقتان لا أكثر: (أ) الجزء العمومي يُعاد بناؤه من `x/y` الملصوقة **دون التحقق أنها تطابق المفتاح الخاص** — عدم تطابق يفشل مغلقًا (`NO_WRAP` دائمًا) لا يفتح ثغرة؛ (ب) واجهة الاستعادة لا تحذر المستخدم أن الملصوق سرّ لا يُرسَل لأحد — تحسين واجهة فقط (R4).
- **`test-device` في `devices.json`:** مفتاحه الخاص وُلّد ورُمي عمدًا (كما توثق `VAULT-INTEGRATION.md`) — لا أحد يستطيع فتح تغليفه، وهو حمل زائد صغير فقط في كل لقطة. يُفضَّل إزالته قبل نشر المالك (R2).

## ٤) الأخطاء العملية

| الحالة | السلوك المفحوص |
|---|---|
| `devices.json` فارغ `[]` | جرّبتها بنفسي (مع استعادة الملف بعدها): التشفير ينجح بـ`wraps: []` + تحذير صريح، واللقطة لا يفتحها أحد — **فشل مغلق صحيح**. |
| اللقطة بلا `wraps` | نفس الحالة أعلاه: `unwrapSnapshot` يرمي `NO_WRAP` قبل أي فك تشفير. |
| فشل فك التشفير عند التحميل | شاشة خطأ + زر إعادة محاولة؛ لا بيانات جزئية أبدًا (الفك ذري: `JSON.parse` بعد فك كامل ناجح فقط). |
| لقطة جديدة تُنشر أثناء جلسة مفتوحة | لا إعادة جلب — الجلسة تحتفظ بالبيانات القديمة في الذاكرة حتى تحديث الصفحة. لا تسرب، لكن البيانات قديمة حتى التحديث. |
| غياب `snapshot.enc.json` من النشر | **الصامت الخطر:** الموقع يرجع لوضع `plain` ويجلب `site-data.json` الواضح دون أي تحذير. لا كود يمنع ذلك؛ الحماية الوحيدة هي خطوة النشر (R1). |
| كاش CDN للقطة | لا `Cache-Control` صريح لـ`/data/snapshot.enc.json` في `vercel.json` — حزمة قديمة مخزنة مؤقتًا قد تُظهر لجهاز مسجل حديثًا `NO_WRAP` حتى إعادة التحقق. تحسين تشغيلي (R3). |
