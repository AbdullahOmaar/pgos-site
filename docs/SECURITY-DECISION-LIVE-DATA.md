## ١. السياق ودوافع القرار

في المرحلة التأسيسية لموقع اوس (البند 3A-316)، اعتمد النظام على **نموذج اللقطة الثابتة المشفرة طرف-لطرف (E2EE Client Snapshot)**:
- خط التوليد (`tools/generate_data.py`) يقرأ المصادر الكانونية (`ops-system/linear-sync`, `ops-system/ledger`, `ops-system/pgos/records`).
- خط التشفير (`tools/encrypt_snapshot.mjs`) يشفر البيانات بمفتاح عشوائي (DEK) ويغلفه بمفاتيح الأجهزة المسجلة عبر ECDH P-256 + HKDF (`tools/devices.json`).
- الناتج يُحزم كملف ثابت `snapshot.enc.json` ويُنشر عبر Vercel.

### أوجه القصور البنيوية في النموذج الثابت أمام التشغيل الحي:
1. **دورة نشر ثقيلة ومكبّلة للحركة:** أي تعديل في Linear (تغيير حالة بند، نقل سبرنت، مشروع جديد كـ Wedora) يتطلب تشغيل خط توليد + تشفير + نشر يدوي مشفر عبر المدير.
2. **مخاطر تجاوز اللقطة الحقيقية:** النشر التلقائي عبر Git يستبدل اللقطة المشفرة بنسخة DEMO المنقاة، مما يفرض منع النشر الآلي وحصره بالمدير يدويًا.
3. **تعارض صريح مع توجيه المالك:** وجه المالك بوضوح بأن تكون المنظومة ديناميكية دون الحاجة لنشر موقع مع كل تحديث مشروع.

لذلك حسم القرار (3A-357/أ) إنشاء **طبقة بيانات حية خفيفة (Supabase Postgres)** مدعومة بمزامنة دورية من Linear كل ~15 دقيقة.

## ٢. القرار الأمني الجوهري

تقرر اعتماد **معمارية هجينة متعددة المستويات (Defense-in-Depth)** تجمع بين سرعة البيانات الحية وصلابة حماية الخزنة:

1. **قاعدة بيانات سحابية بحساب مالك فقط مع سياسات أمان صفية صارمة (Strict RLS):**
   - حظر كامل ومطلق لوصول الدور العام (`anon` role). لا يمكن لأي طلب غير مصادق عليه قراءة أو كتابة أي بايت.
   - حصر استعلامات القراءة للمالك فقط (`authenticated` role مقترن بمعرف المالك أو بريده المعتمد).
   - حصر الكتابة والتعديل بعامل المزامنة الخلفي فقط عبر مفتاح الخدمة المشفر في بيئة الخادم (`service_role`).

2. **بقاء بوابة الجهاز (Device Gate / Vault) كواجهة دخول وحيدة للمتصفح:**
   - واجهة اوس لا تعرض شاشة تسجيل دخول تقليدية مفتوحة للعامة، بل تحتفظ ببوابة الخزنة المستندة لمفاتيح الأجهزة (Hardware-bound Device Authentication).
   - الجهاز غير المسجل في `tools/devices.json` يُرفض فورًا عند عتبة المتصفح (Browser Threshold) قبل توجيه أي طلب لقاعدة البيانات.
   - حتى لو تسرب رابط Supabase أو المفتاح العام للواجهة (VITE_SUPABASE_ANON_KEY)، فإن RLS يرفض الاستعلامات (Zero Data Access)، وبوابة الجهاز ترفض فتح الشاشات.

## ٣. مصفوفة المقارنة الأمنية والتشغيلية

| وجه المقارنة | نموذج اللقطة المشفرة القديم | نموذج البيانات الحية المقترح (RLS + Device Gate) |
|---|---|---|
| **زمن انعكاس التغييرات** | ساعات (مع كل نشر يدوي) | لحظي / تزايدي (~15 دقيقة عبر عامل المزامنة) |
| **آلية النشر** | يدوي مشفر فقط (خطر الاستبدال بـ DEMO) | الموقع يُنشر مرة واحدة؛ البيانات تتجدد تلقائيًا |
| **حماية البيانات أثناء التخزين (At Rest)** | تشفير AES-256-GCM بملف العميل | تشفير أقراص Supabase + RLS + حظر الدور العام |
| **حماية البيانات أثناء النقل (In Transit)** | HTTPS فقط للملف المشفر | TLS 1.3 مشفر + توكنات JWT موقعة بمفتاح المالك |
| **التحكم بالوصول (Access Control)** | تشفير بمفتاح الجهاز العمومي | فحص هوية الجهاز محليًا + تفويض RLS على الخادم |
| **التوافر عند انقطاع الشبكة** | نعم (كاش محلي) | نعم (الاحتفاظ بنموذج DEMO وFallback الكاش المحلي) |
| **مخاطر تسرب المفاتيح العامة** | لا خطورة (المفتاح العمومي لا يفك التشفير) | لا خطورة (دور `anon` محروم من صلاحية SELECT) |

## ٤. نموذج التهديدات وإجراءات التخفيف (STRIDE Analysis)

### ٤.١ انتحال الهوية (Spoofing)
- **التهديد:** محاولة طرف خارجي قراءة بيانات الشركة من واجهة اوس المنشورة.
- **التخفيف:** التحقق الثنائي:
  1. طبقة الجهاز: بوابة الخزنة تطالب بالمفتاح الخاص المخزن في `IndexedDB` غير القابل للتصدير (`extractable: false`).
  2. طبقة الخادم: طلبات قاعدة البيانات تتطلب JWT صالحًا لحساب المالك؛ الـ `anon key` لا يملك صلاحية القراءة.

### ٤.٢ العبث بالبيانات (Tampering)
- **التهديد:** محاولة حقن بنود مهام أو تعديل حالات مشاريع من خارج Linear.
- **التخفيف:**
  - جداول اوس للقراءة فقط بالنسبة لواجهة المستخدم؛ لا يوجد أي `INSERT` أو `UPDATE` policy للمستخدم العادي في RLS.
  - عامل المزامنة هو الكيان الوحيد المخول بالكتابة عبر قناة آمنة ومفاتيح مشفرة بالبيئة (`SUPABASE_SERVICE_ROLE_KEY`).
  - المزامنة حتمية (Deterministic Idempotent Upserts) وتعتمد Linear كمصدر حقيقة وحيد.

### ٤.٣ إنكار التصرف (Repudiation)
- **التهديد:** حدوث تعارض أو فقدان في مزامنة البنود دون معرفة المتسبب.
- **التخفيف:**
  - جدول `sync_runs` يسجل كل دورة مزامنة: بصمة الوقت، عدد البنود، الحالات المتغيرة، وأي استثناءات.
  - الاحتفاظ بأختام Linear الكانونية (`updatedAt`, `completedAt`).

### ٤.٤ إفشاء المعلومات (Information Disclosure)
- **التهديد:** فحص شبكة المتصفح واستخراج بيانات المشروعات الحساسة أو أسماء العملاء.
- **التخفيف:**
  - استجابة PostgREST لأي استعلام غير مصادق عليه تعيد مصفوفة فارغة `[]` أو رمز الخطأ `401 Unauthorized` / `403 Forbidden`.
  - عدم تخزين أي أسرار أو توكنات إدارية في كود الواجهة أو إعدادات Vercel العامة.

### ٤.٥ حجب الخدمة (Denial of Service)
- **التهديد:** استنزاف كوتا Supabase المجانية أو إغراق واجهة API.
- **التخفيف:**
  - المزامنة تعمل داخليًا كل ~15 دقيقة بمعدل استهلاك منخفض جدًا (استعلام واحد تزايدي).
  - وجود وضع الاستعداد (Fallback DEMO Mode) يضمن بقاء واجهة اوس تعمل وظيفيًا حتى لو تعطلت قاعدة البيانات أو نفدت الكوتا.

## ٥. قواعد التنفيذ الصارمة لطبقة البيانات الحية

1. **قاعدة حظر الأسرار (Zero Secrets in Code/Logs):**
   - تُمنع كتابة أي مفتاح Supabase Service Role أو Linear API Token في ملفات الريبو أو ملفات التتبع أو مخرجات الأدوات.
   - كافة المتغيرات تُحقن عبر متغيرات البيئة فقط (`.env.local` المغطاة بـ `.gitignore`، أو خزن البيئة المشفرة).

2. **قاعدة الهجرات العبارة-عبارة (Statement-by-Statement Migrations):**
   - كافة تعديلات المخطط تُكتب في ملفات SQL متسلسلة تقبل التطبيق التزايدي والتراجع (Reversible DDL).
   - تفعيل RLS يكون جزءًا لا يتجزأ من أمر إنشاء الجدول (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY`).

3. **حتمية المزامنة (Idempotent Sync Invariant):**
   - تشغيل عامل المزامنة 100 مرة متتالية على نفس بيانات Linear يُنتج نفس الحالة الرياضية بدقة (Zero Duplication, Zero Drifts).
   - مفتاح المطابقة هو `uuid` الكانوني لـ Linear مع التحقق من `updatedAt`.

4. **استمرارية وضع الديمو الاحتياطي:**
   - الحفاظ التام على محاكاة البيانات (`DEMO mode`) كشبكة أمان للواجهة في حال غياب الاتصال بقاعدة البيانات.
