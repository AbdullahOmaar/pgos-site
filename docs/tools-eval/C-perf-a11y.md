# تقييم أدوات — المجموعة ج: الأداء والتحمّل وإمكانية الوصول والمرونة والإيميل

**النطاق:** k6، Locust، axe-core، Pa11y، Biome، Unlighthouse، Toxiproxy، Mailpit.
**تاريخ البحث:** 22 نوفمبر 2026 — بحث ويب حي، مصادر رسمية أولًا (مواقع المشاريع، GitHub، npm، وثائق Supabase وGrafana).
**السياق الحاكم:** ستاك الشركة React + TypeScript + Supabase + Vercel + PWA (موبايل أولًا، مستخدمون مصريون على أجهزة متوسطة)، CI على GitHub Actions، صفر تكلفة سيرفر مدفوع، والقائم حاليًا: oxlint للّينت، حارس حجم حزمة ≤5%، Lighthouse يدوي أحيانًا.
**قاعدة التبنّي:** أي أداة تُعتمد تدخل أولًا «CI معلوماتي» (تُشغَّل وتُرفع تقاريرها دون أن تحجب الدمج)، ولا تتحول إلى بوابة حاجبة إلا بعد فترة استقرار وقياس ضوضاء.

> ملحوظة منهجية: أرقام الإصدارات والتواريخ أدناه كما ظهرت في المصادر بتاريخ البحث. أي ادعاء منسوب أصلًا إلى Gemini عومل كادعاء غير متحقق منه حتى أكدته المصادر الأولية، ووُسم صراحة في مكانه.

## أولًا: مقارنة مباشرة k6 مقابل Locust (لفحصي ٨ و٤١)

الفحصان المعنيّان: **٨ — اختبارات التحمّل (load/stress/spike/soak)** و**٤١ — Rate Limiting واختبار إساءة الاستخدام تحت ضغط متسارع**. الأداتان تصلحان تقنيًا للاثنين، والاختيار عندنا قرار لغة وصيانة لا قرار قدرة:

| البعد | Grafana k6 | Locust |
|---|---|---|
| لغة كتابة الاختبارات | JavaScript/TypeScript — لغة الستاك نفسه | Python — لغة ثانية خارج ستاك التطبيق |
| الترخيص | AGPL-3.0 (للبيناري مفتوح المصدر) | MIT |
| التشغيل الموزّع | يحتاج k6 Operator على Kubernetes أو السحابة المدفوعة لتوزيع حقيقي | Master/Worker مدمج في المشروع مفتوح المصدر |
| بوابات CI | Thresholds مدمجة تتحول إلى Exit Code غير صفري (99 عند فشل العتبة) + أكشنات رسمية من Grafana لـ GitHub Actions | Headless مع `--exit-code-on-error`؛ العتبات تُكتب يدويًا في الكود |
| كلفة التشغيل عندنا | صفر: بيناري واحد يعمل على GitHub Actions runner | صفر: pip/Docker على نفس الـ runner |
| حدود عملية | مولّد حمل واحد (الـ runner) يكفي حجمًا لمرحلتنا الحالية | نفس الحد تقريبًا لكل مولّد؛ التوزيع أسهل عند الحاجة |

**واقع التشغيل ضد بيئتنا (ينطبق على الأداتين):**
- **مَن يشغّلها:** GitHub Actions (workflow ليلي أو يدوي `workflow_dispatch`) — لا سيرفر دائم، التزامًا بقاعدة صفر تكلفة سيرفر.
- **ضد ماذا:** مشروع Supabase **تجريبي (Staging) منفصل** + نشر Vercel Preview — وممنوع ضد الإنتاج. وثائق Supabase الرسمية نفسها توصي باختبار التحمّل «ويفضّل على بيئة staging» وتذكر k6 بالاسم كمثال، وتنبّه إلى أن المنصة لديها حمايات ضد موجات الترافيك (burst safeguards)، وأن حدود Auth (خصوصًا إرسال الإيميلات وعمليات الدخول من IP واحد) ستظهر في النتائج كأخطاء ما لم تُضبط حسابات/رموز اختبار مسبقًا — أي إن جزءًا من «الفشل» في أول تشغيل سيكون حدود المنصة لا عيوب التطبيق، ويجب قراءته كذلك.
- **فحص ٤١ تحديدًا:** اختبار الإساءة يُوجَّه إلى نقاط Auth وREST في بيئة التجربة للتحقق أن حدود المعدّل (Rate Limits) المضبوطة في لوحة Supabase تعمل فعلًا (استجابات 429 بعد الحد)، لا لمحاولة إسقاط الخدمة؛ والضغط «المتسارع» يكون بمراحل قصيرة (ramp) داخل حدود ما تتحمله خطة Supabase التجريبية.

## ١) Grafana k6 — اختبارات التحمّل والإساءة

**حقائق بمصادر:**
- مفتوح المصدر بترخيص **AGPL-3.0** (ملف LICENSE في مستودع grafana/k6)؛ النسخة السحابية Grafana Cloud k6 مدفوعة بوحدة Virtual User Hour (خطة مجانية بحد 500 VUh شهريًا حسب صفحة أسعار Grafana) — **لا نحتاج السحابة إطلاقًا**؛ البيناري المحلي/CI مجاني بلا حدود مقاعد أو ساعات.
- الصيانة: نشطة بقوة في 2026؛ خط إصدارات v2 وصل إلى v2.3.0 (سبتمبر 2026) مع استمرار صيانة خط v1 (v1.8.2 في أكتوبر 2026)، وكوميتات حديثة حتى نوفمبر 2026.
- تكامل CI رسمي: `grafana/setup-k6-action` و`grafana/run-k6-action` على GitHub Marketplace من الناشر نفسه، والعتبات (thresholds) مثل `p(95)<500` و`rate<0.01` تُفشل التشغيل بكود خروج غير صفري — أي بوابة جاهزة دون كود وسيط.

**الملاءمة والتداخل:**
- لا يتداخل مع أي أداة قائمة؛ يملأ فجوة حقيقية: لا توجد عندنا اليوم أي اختبارات تحمّل آلية.
- لغة الاختبارات JS/TS تعني أن نفس فريق التطبيق يكتبها ويصونها، وأن سيناريوهاتها يمكن أن تعيد استخدام منطق المصادقة والبيانات من كود التطبيق.
- ملحوظة الترخيص: AGPL تعني التزامات عند **تعديل k6 نفسه وتوزيعه/تقديمه كخدمة**؛ استخدامنا الداخلي (تشغيل البيناري كما هو في CI) لا يرتب أي التزام عملي على كود تطبيقنا — لكن يجب ألا نبني فوقه منتجًا موزعًا دون مراجعة قانونية.

**الحكم: ✅ تبنّي.**
- **أين يدخل:** GitHub Actions كـ workflow منفصل (ليلي + تشغيل يدوي قبل الإطلاقات الكبيرة) ضد Supabase Staging وVercel Preview، **معلوماتي أولًا**: تُرفع النتائج كـ artifacts وتُعرض العتبات دون حجب الدمج في المرحلة الأولى.
- **أي فحص يخدم:** ٨ (تحمّل) أساسًا، و٤١ (إساءة/Rate Limiting) بنفس السكربتات مع سيناريوهات ramp وتركيز على نقاط Auth.
- **شرط قبل التحول لبوابة حاجبة:** ضبط خط أساس (baseline) من ٣–٥ تشغيلات مستقرة، وحسابات اختبار مُصادق عليها مسبقًا حتى لا تلوث حدود Auth النتائج.

**ادعاءات Gemini محل فحص:** أي تصوير لـ k6 على أنه «مجاني بالكامل بلا قيود» غير دقيق جزئيًا: المجاني هو البيناري مفتوح المصدر؛ التوزيع السحابي الرسمي مدفوع بوحدة الاستخدام. وادعاء أن AGPL «لا فرق بينه وبين MIT» (إن ورد) غير صحيح من حيث المبدأ، وإن كان أثره العملي على استخدامنا الداخلي معدومًا.

## ٢) Locust — اختبارات التحمّل (بديل k6)

**حقائق بمصادر:**
- مفتوح المصدر بترخيص **MIT** (أنقى ترخيصًا من k6)، اختباراته كود Python عادي (كل مستخدم افتراضي = كلاس)، وواجهة ويب مدمجة للتشغيل التفاعلي.
- الصيانة: نشطة؛ أحدث إصدار 2.47.0 (21 أكتوبر 2026) ويتطلب Python 3.11+؛ النشرات متكررة طوال 2026، ومايكروسوفت ترعى صيانته وتقدّم تشغيله المُدار عبر Azure Load Testing (وهو خيار مدفوع لا يعنينا).
- التوزيع Master/Worker مدمج في النسخة مفتوحة المصدر — ميزة حقيقية على k6 OSS عند أحمال ضخمة متعددة المولدات.

**الملاءمة والتداخل:**
- **ازدواجية كاملة الوظيفة مع k6**: نفس الفحصين (٨ و٤١)، نفس نموذج التشغيل في CI، نفس الأهداف. اعتماد الأداتين معًا يعني صيانة مجموعتي سكربتات لقياس الشيء نفسه.
- كلفة خفية: إدخال Python كبيئة اختبار ثانية (إصدارات، تبعيات، أسلوب كتابة) في فريق ستاكه TypeScript؛ خبرة Python عندنا موجودة في أدوات PGOS الداخلية لا في اختبارات التطبيق.

**الحكم: ❌ رفض (ازدواجية) — مع محفّز إعادة نظر موثق.**
- السبب: k6 يغطي الحاجة بلغة الستاك وبوابات CI أنضج؛ لا قيمة مضافة تبرر أداة موازية اليوم.
- يُعاد النظر فقط إذا: (أ) احتجنا توزيع حمل متعدد المولدات بلا Kubernetes/سحابة، أو (ب) نمت اختبارات Python أصلًا حول التطبيق فأصبحت الكتابة به أرخص.

**ادعاءات Gemini محل فحص:** ترخيص MIT ونشاط الصيانة صحيحان. أي ادعاء بأن Locust «أسهل في CI» من k6 غير مدعوم: بوابات k6 (thresholds + أكشنات رسمية) أقل كودًا وسيطًا من عتبات Locust اليدوية.

## ٣) axe-core — فحص إمكانية الوصول الآلي

**حقائق بمصادر:**
- محرك قواعد مفتوح المصدر من Deque بترخيص **MPL-2.0** (copyleft على مستوى الملف: يلزم فقط عند تعديل ملفات axe نفسه)، مجاني بالكامل بما فيه الاستخدام التجاري وCI.
- يغطي WCAG 2.0/2.1/2.2 بمستويات A/AA/AAA؛ إصدارات فرعية كل ٣–٥ أشهر تقريبًا (وصل إلى 4.13 في أغسطس 2026 كما يظهر في تبعيات Pa11y 10) — صيانة نشطة ومستقرة منذ سنوات، وهو المحرك نفسه داخل Lighthouse وداخل إرشادات Playwright الرسمية لاختبار الوصول.
- حدّ موثق من الناشر نفسه: الأتمتة تكشف في المتوسط نحو **57%** فقط من مشكلات WCAG؛ الباقي (مصائد لوحة المفاتيح، المعنى، الفهم) يحتاج فحصًا يدويًا — أي إن axe شرط لازم لا كافٍ لفحص ١٤.

**الملاءمة والتداخل:**
- يدخل في طبقتين عندنا دون بنية جديدة: (أ) اختبارات مكوّنات Vitest عبر `vitest-axe`/`jest-axe` على DOM المُصيَّر، (ب) اختبارات E2E القائمة (Puppeteer/Playwright) عبر حقن axe في الصفحة بعد التفاعلات.
- لا يتداخل مع oxlint (قواعد jsx-a11y في اللينتر ثابتة وقت الكتابة، وaxe يفحص DOM الحي بعد التصيير — طبقتان متكاملتان لا مكررتان).
- مهم خصوصًا لواقعنا: واجهات عربية RTL على شاشات صغيرة — axe يمسك التباين والأسماء المفقودة وأدوار ARIA الخاطئة، وهي أخطاء تتكرر في الواجهات ثنائية الاتجاه.

**الحكم: ✅ تبنّي.**
- **أين يدخل:** CI معلوماتي أولًا داخل حزم Vitest وE2E القائمة، بقاعدة فشل مبدئية على الانتهاكات الحرجة (critical) فقط بعد فترة معايرة، وتقرير كامل يُرفع كـ artifact.
- **أي فحص يخدم:** ١٤ (WCAG 2.2 AA) — الجزء الآلي منه؛ ويبقى الجزء اليدوي (قارئ شاشة + لوحة مفاتيح) بندًا منفصلًا في نفس الفحص لا تغطيه الأداة.

**ادعاءات Gemini محل فحص:** نسبة «57%» رقم Deque التسويقي عن متوسط ما تكشفه الأتمتة — صحيح كترتيب حجم لا كوعد تغطية لتطبيق بعينه؛ أي صياغة توحي بأن axe وحده «يحقق WCAG» خاطئة.

## ٤) Pa11y — فحص وصول من سطر الأوامر على URL

**حقائق بمصادر:**
- أداة CLI وNode API من مشروع Pa11y، ترخيص **LGPL-3.0**، مجانية؛ أحدث إصدار **10.0.0 (27 أغسطس 2026)** يتطلب Node 22+ ويحدّث Puppeteer إلى 25 وaxe-core إلى 4.13 — صيانة نشطة (9.x في فبراير 2026، و10 بعدها).
- بنيويًا هي **غلاف تشغيل**: تُطلق متصفحًا (Puppeteer) على URL جاهز وتشغّل محركين — axe نفسه، وHTML_CodeSniffer — وتجمع النتائج بتقارير وعتبات (threshold) جاهزة.

**الملاءمة والتداخل:**
- **ازدواجية مباشرة مع axe-core المعتمد أعلاه**: نصف نتائجها على الأقل يأتي من نفس المحرك، والفارق الحقيقي هو HTML_CodeSniffer ونموذج «افحص URL منشورًا دون كود اختبار».
- ميزتها الوحيدة المميزة عندنا: فحص سريع لنشر Preview منشور فعلًا (بما فيه صفحات لا تغطيها اختبارات المكونات) بسطر واحد، لكنها تضيف تبعية ثقيلة (متصفحها الخاص) وطبقة إعداد موازية.

**الحكم: ⏸ تأجيل — بسبب الازدواجية.**
- لا تُدخل إلى CI الآن؛ axe-core داخل الاختبارات يغطي الفحص ١٤ بعمق أكبر (حالات تفاعلية، مكوّنات).
- استخدام ظرفي مسموح دون «تبنٍّ»: `npx pa11y <preview-url>` يدويًا عند الحاجة لتدقيق سريع على نسخة منشورة، دون إضافتها إلى تبعيات المشروع.
- يُعاد النظر إذا ظهرت حاجة دورية لتدقيق URL خارجي لا تملكه الاختبارات (مثل صفحات هبوط تسويقية منفصلة عن التطبيق).

**ادعاءات Gemini محل فحص:** أي تقديم لـ Pa11y وaxe-core كأداتين «مختلفتين» تكمل إحداهما الأخرى مضلل جزئيًا: Pa11y تتضمن axe داخلها؛ الاختلاف في نموذج التشغيل لا في محرك القواعد الأساسي.

## ٥) Biome — لينتر وفورماتر موحّد (مقابل oxlint + Prettier القائمين)

**حقائق بمصادر:**
- أداة Rust واحدة تجمع اللينت والتنسيق، ترخيص **MIT أو Apache-2.0** (خيار المستخدم)، مجانية؛ الإصدارات نشطة جدًا (سلسلة 2.x؛ ظهر 2.6.8 في نوفمبر 2026 في توزيعات الأنظمة).
- التنسيق متوافق مع Prettier بنسبة **97%** (رقم المشروع نفسه)، وقواعد اللينت بالمئات (450+ وتتزايد)، ومنذ v2 (يونيو 2025) قواعد واعية بالأنواع بمحرك استدلال خاص — قُدّر عند إطلاق v2 بأنه يمسك نحو 75% مما تمسكه قواعد typescript-eslint النوعية.
- المقابل القائم عندنا تطوّر أيضًا: oxlint (MIT، من مشروع Oxc/VoidZero) تجاوز 800 قاعدة، وأضاف في 2026 لينتًا واعيًا بالأنواع عبر tsgo (منفذ Go لمترجم TypeScript)، وهو أسرع من Biome في اللينت الصرف بنحو الضعفين حسب بنشمارك Oxc نفسه؛ وفورماتر Oxc المقابل (Oxfmt) ما زال بيتا.

**كلفة الهجرة مقابل المكسب (واقعنا تحديدًا):**
- الكلفة: إعادة تنسيق قاعدة الكود كلها دفعة واحدة (Diff ضخم يلوث Blame ويربك أي فروع مفتوحة)، إعادة كتابة إعدادات، فجوات قواعد/بلاجنات قد تظهر متأخرًا، وفقدان نضج منظومة Prettier في ملفات غير JS (Markdown/YAML وبلاجناتها ليست بنفس التغطية).
- المكسب: أداة واحدة بدل اثنتين، وسرعة تنسيق أعلى — وكلاهما مكسب راحة لا قدرة: لا فحص من فحوص الجدول يتوقف على Biome، وفحص ١٢ (بوابات lint + أنواع) يعمل اليوم بـ oxlint + tsc.

**الحكم: ⏸ تأجيل — كلفة هجرة لا يقابلها مكسب قدرة الآن.**
- يبقى oxlint + Prettier هو المعيار في المشاريع القائمة.
- محفّزات إعادة النظر: (أ) بدء مشروع جديد من الصفر (الهجرة هناك مجانية تقريبًا — Biome خيار مشروع جديد مشروع)، (ب) استقرار Oxfmt وخروج oxlint من سباق الميزات، (ج) أن تصبح سرعة التنسيق عنق زجاجة فعليًا في CI (ليست كذلك اليوم).

**ادعاءات Gemini محل فحص:** صياغة «Biome يستبدل ESLint وPrettier بالكامل» صحيحة كطموح مشروع، لكنها تخفي فجوتين موثقتين: توافق تنسيق 97% لا 100% (أي Diff إجباري عند التبنّي)، وتغطية نوعية جزئية (~75% عند إطلاق v2) تجعله غير كافٍ وحده بديلًا عن tsc/typescript-eslint في فحوص الأنواع الصارمة.

## ٦) Unlighthouse — Lighthouse على مستوى الموقع كله

**حقائق بمصادر (مع تحقق مباشر من حالة الصيانة):**
- أداة تلفّ Lighthouse الرسمي وتزحف على الموقع كله (اكتشاف روابط + تشغيل متوازٍ + لوحة نتائج مجمعة)، ترخيص **MIT**، مجانية.
- **حالة الصيانة كما تحققت منها في 22 نوفمبر 2026:** المستودع (harlan-zw/unlighthouse) **غير مؤرشف**، وآخر دفع (push) بتاريخ 21 نوفمبر 2026، وآخر إصدار على npm هو **0.19.1 (أوائل أكتوبر 2026)**. إذن الادعاء بأن المشروع «ميت/مؤرشف» — إن ورد — **غير صحيح**.
- لكن الصورة الكاملة أقل راحة: المشروع **بصيّان واحد فعليًا** (Harlan Wilton)، وإيقاع الإصدارات أبطأ من سنواته الأولى، وتكامل Vite الرسمي موسوم على npm بأنه **مهجور: «Vite integration is no longer supported — use CLI directly»**؛ والاستخدام المدعوم الآن هو CLI فقط.

- لا تداخل مع أداة قائمة: Lighthouse اليدوي يبقى للصفحات الحرجة واحدة-واحدة.

**الحكم: ⏸ تأجيل التبنّي الرسمي — يعمل يدويًا بـnpx على الصفحات العامة قبل الإطلاق.**
- لا بوابة CI عليه ولا اعتماد على تكاملاته (تكامل Vite مهجور رسميًا).
- يُعاد النظر إذا اتسع عدد الصفحات العامة أو احتجنا تقريرًا مجمعًا دوريًا قبل كل إطلاق.

**ادعاءات Gemini محل فحص:** «Unlighthouse ميت/مؤرشف» — **غير صحيح** (تحقق مباشر من GitHub API: `archived: false`، آخر push ‏21 نوفمبر 2026، إصدار 0.19.1 أكتوبر 2026). الحقيقة الدقيقة: حي لكن بصيّان واحد وإيقاع أبطأ — وهذا سبب التأجيل، لا «الموت».

## ٧) Toxiproxy — حقن أعطال الشبكة (بطء/انقطاع) في الاختبارات

**حقائق بمصادر:**
- بروكسي TCP من Shopify لحقن الأعطال (زمن استجابة، انقطاع، حدود نطاق)، ترخيص **MIT**، مجاني؛ آخر إصدار موثق **v2.13.0 (أكتوبر 2026)** والمشروع نشط.
- يعمل كخدمة وسيطة: العميل يتصل بالبروكسي والبروكسي يمرّر للخدمة الحقيقية مع الأعطال المحقونة — أي يحتاج نقطة إدخال يمر عبرها ترافيك الاختبار.

**الملاءمة والتداخل:**
- يخدم فحص ٤٤ (مرونة وحقن أعطال) نظريًا، لكن **معماريًا لا يناسبنا**: ترافيك المتصفح عندنا يذهب مباشرة إلى Supabase مُدار (PostgREST/Auth) — لا نقطة إدخال للبروكسي في المنتصف، والحلقة الأهم أصلًا عند المزود نفسه لا عندنا.
- البديل الفوري المتاح بلا أداة جديدة: اعتراض/محاكاة الشبكة داخل Playwright (تأخير وفشل طلبات محدد) + اختبار Offline للـPWA — يغطيان السيناريوهات الحرجة (انقطاع أثناء إرسال نموذج، بطء تحميل قائمة) مباشرة في بيئة المتصفح الحقيقية.

**الحكم: ⏸ تأجيل — بسبب معماري، لا بسبب الأداة.**
- لا يُدخل إلى CI الآن. محفّز التبنّي الوحيد الموثق: تشغيل بيئة Supabase محلية في CI (عندها يصبح للبروكسي نقطة إدخال حقيقية بين الاختبارات وقاعدة محلية).
- ممنوع في الإنتاج (كما نص الفحص نفسه).

**ادعاءات Gemini محل فحص:** تقديم Toxiproxy كأداة «في CI» بلا قيد يخفي شرط نقطة الإدخال — في ستاك مُدار بالكامل الشرط غير متحقق أصلًا.

## ٨) Mailpit — اعتراض الإيميلات في الاختبار (بدل إرسال حقيقي)

**حقائق بمصادر:**
- خادم SMTP وهمي + واجهة ويب لعرض الرسائل الملتقَطة، ترخيص **MIT**، مجاني؛ إصدارات شهرية نشطة — آخر إصدار موثق **v1.33.1 (7 نوفمبر 2026)**.
- **مدمج أصلًا في Supabase CLI المحلي**: وثائق Supabase الرسمية تنص أن `supabase start` يشغّل Mailpit على `localhost:54324` لالتقاط إيميلات بيئة التطوير المحلية — أي أن الأداة موجودة عندنا فعليًا بلا تثبيت ولا تكلفة.
- **ادعاء توقف MailHog — صحيح ومتحقق من المصدر الأولي:** آخر إصدار v1.0.1 (أغسطس 2020)، وآخر كوميت أغسطس 2022، وREADME ‏Mailpit نفسه يصرّح بذلك ويربط بتصريح التوقف في مستودع MailHog.

**الملاءمة والتداخل:**
- يخدم فحص ٤٥ مباشرة: اختبارات SMTP/Edge Functions تلتقط الرسائل من Mailpit وتتحقق من المحتوى والروابط دون أي إرسال حقيقي.
- لا تداخل مع أداة قائمة؛ ولا سيرفر إضافي في CI (service container خفيف أو الاستفادة من نسخة Supabase المحلية نفسها).

**الحكم: ✅ تبنٍّ — شبه مجاني فعليًا.**
- يُضاف لـCI كـservice container لاختبارات SMTP/Edge Functions، ويُستخدم محليًا عبر نسخة Supabase CLI المدمجة.
- لا حاجة لأي بديل مدفوع أو مستضاف.

**ادعاءات Gemini محل فحص:** التوصية بـMailpit سليمة، وادعاء توقف MailHog صحيح — لكن أي رقم إصدار غير v1.33.1 (الموثق في 7 نوفمبر 2026) يُوسم «غير متحقق» ولا يُعتمد.
