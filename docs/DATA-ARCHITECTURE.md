# معمارية بيانات موقع PGOS — وثيقة تصميم تقنية

**الحالة:** مسودة تصميم للمراجعة — مبنية على قراءة فعلية للمشروعين القائمين (2026-11-22)، لا على افتراضات.
**النطاق:** موقع قراءة (Read-Only) يعرض حوكمة الشركة: سجلات PGOS + سجل الشركة + بنود Linear + قرارات المقر + حالة حارس الاكتمال + مرجع الشركة + التقارير.
**خارج النطاق في هذه الوثيقة:** أي كتابة/تعديل من الموقع، أي استبدال لـ Linear أو مقر Drive أو السجل — الموقع **مرآة عرض**، ومصادر الحقيقة تبقى كما حسمها DEC-TOTO-001 وملف التبنّي.

## ١. البنية المقترحة للموقع

### الحكم: نعم — نفس مكدّس تطبيق المدرس، بنفس إصداراته الرئيسية، مع حذف طبقة Supabase من المرحلة الأولى

**React 19 + TypeScript + Vite 8 + Tailwind v4 + React Router 7**، والبناء `tsc -b && vite build`، والفحص `oxlint`، والنشر مشروع Vercel مربوط بنفس طريقة `teacher-app` (مجلد `.vercel/`، إخراج `dist` الافتراضي).

**الأسباب (كل سبب مربوط بدليل):**

1. **قاعدة معرفية واحدة:** كل بوابات الجودة ودروس النشر والمراجعة المتراكمة في مسار تطبيق المدرس تنطبق حرفيًا — لا منحنى تعلّم ولا أدوات جديدة تُصان.
2. **إعادة استخدام مباشرة:** `index.css` (الثيم كاملًا بمتغيراته وثيمه الداكن)، وخط IBM Plex Sans Arabic وإعداد RTL، ومكونات `components/ui` (Card/Button/EmptyState/Sheet/حالات التحميل والخطأ)، ونمط `AppShell` — تُنسخ وتُكيّف لا تُعاد كتابتها. الهوية واحدة لأن الشركة واحدة.
3. **الحجم يسمح بالبساطة:** كامل بيانات الموقع الحالية أقل من ~100KB JSON (الحمولة الأكبر 85KB) — لا حاجة لقاعدة بيانات لعرضها (انظر القسم ٢).
4. **ما يُحذف ولماذا:** `@supabase/supabase-js` لا يدخل المرحلة الأولى (لا خلفية أصلًا)؛ `@tanstack/react-query` يبقى خفيف الاستخدام لجلب ملفات JSON المحلية مع كاش وإعادة محاولة، أو يُستغنى عنه بـ `fetch` بسيط — القرار عند التنفيذ، والأبسط يُفضّل؛ `@tanstack/react-table` يدخل فقط إن احتاجت جداول البنود/القيود فرزًا وفلترة ثقيلة، وإلا تُبنى الجداول بمكونات UI القائمة.

## ٢. نموذج البيانات

### ٢.١ المبدأ الحاكم

الموقع لا يقرأ المصادر الخام مباشرة أبدًا. بين المصادر والمتصفح طبقة تحويل واحدة (**خط الأنابيب**، القسم ٤) تنتج **نموذج عرض موحّدًا** (View Model) بملفات JSON ثابتة. كل ملف مولّد يحمل بصمته ومصدره ووقت توليده، وكل عنصر معروض قابل للتتبع إلى مصدره الأصلي (قيد/سجل/بند/مستند) برابط أو معرّف — تطبيقًا لقاعدة «لا مرايا صامتة» في PGOS وانحراف D-1.

### ٢.٢ نموذج العرض (أنواع TypeScript مقترحة في `src/types/index.ts`)

```ts
// غلاف كل ملف مولّد — يُبنى منه شريط «حداثة البيانات» في كل صفحة
interface GeneratedFileMeta {
  generatedAt: string;          // ISO بتوقيت القاهرة
  generator: string;            // اسم/إصدار سكربت التوليد
  sources: SourceStamp[];       // بصمة كل مصدر دخل في هذا الملف
}
interface SourceStamp {
  source: 'ledger' | 'pgos-records' | 'linear-payload' | 'guard' | 'drive-hq' | 'reference';
  ref: string;                  // مسار الملف أو معرّف المستند
  sha256: string;               // بصمة محتوى المصدر لحظة التوليد
  sourceModifiedAt: string;     // آخر تعديل معروف للمصدر
  stale: boolean;               // تجاوز عتبة القدم الخاصة بهذا المصدر (القسم ٤.٣)
}
```

### ٢.٣ تحويل كل مصدر — من الخام إلى العرض

1. **سجلات PGOS (`pgos/records/*.json`):** تحويل شبه مباشر ١:١ — الصيغة مصممة آليًا أصلًا. الإضافات الوحيدة: فهرس عكسي للروابط (من كل WorkOrder إلى Evidence/قراراته، ومن كل مشروع إلى سجلاته)، والتحقق البنيوي قبل النشر: معرّفات فريدة، وكل `project_id`/`work_order_id`/`approval_ref` يشير إلى سجل موجود — كسر أي رابط = فشل توليد (لا صفحة بسجل يتيم صامت). الأنواع التسعة في قوالب PGOS تُدعم في العرض حتى لو لم يوجد منها إلا خمسة أنواع حاليًا.
2. **السجل (`company-ledger.jsonl`):** يُقرأ سطرًا سطرًا (JSONL)، يُتحقق من السلسلة بـ `ledger.py verify` **قبل** أي تحويل — سلسلة مكسورة = إيقاف النشر كله ووضع شارة حمراء على آخر نسخة صالحة، لا نشر بيانات مشكوك فيها. ثم يُرتّب تنازليًا زمنيًا، وتُحسب لكل achievement رباعيته من `refs`/`legs` وحالة Linear من الحمولة وحضور اللوحة كما يفعل الحارس.
3. **Linear (`linear-sync/payload.json`):** الحمولة القائمة هي المدخل — لا استدعاء API جديدًا من خط الأنابيب في المرحلة الأولى (المزامنة الحالية كل ساعتين تغذي اللوحة أصلًا، والموقع يركب عليها). التحويل: ربط `projectUuid` بمعرّف المشروع المقروء، اشتقاق عدّادات المشاريع والحالات، ووسم الوصف المختصر. **تحقق صف-بصف إلزامي** (درس تقرير المزامنة): عدد البنود والمعرّفات الفريدة وتوزيع الحالات يُقارن بين الخام والمولّد، وأي اختلاف يوقف التوليد.
4. **قرارات Drive:** انظر ٢.٤ — المصدر الوحيد غير الملفّي، ويُعامل بحذر خاص.
5. **المرجع والقوالب:** `COMPANY-REFERENCE.md` و`templates/*.md` تُحوّل Markdown → HTML وقت التوليد (محول Markdown بسيط داخل خط الأنابيب أو مكتبة عرض في الواجهة — الأفضل وقت التوليد: HTML جاهز = صفر تكلفة تشغيل وبحث نصي أبسط)، والتقارير تُملأ من نفس JSON المولّد فلا تنحرف أرقام التقرير عن أرقام الموقع أبدًا.

### ٢.٤ قرارات مقر Drive — معاملة خاصة

سجل قرارات الشركة يعيش في **Google Doc داخل مقر Drive**، وهو الكانوني الواحد للقرارات (D-1)، ولا توجد له نسخة ملفية محلية في `ops-system`. ثلاث حقائق تحكم التصميم:

- **لا قراءة حية من المتصفح** إلى Drive (تتطلب OAuth/مفاتيح — مرفوض، انظر ٢.٥-ج).
- التصدير يتم في بيئة التشغيل الحالية (حيث توجد أدوات Drive المتصلة أصلًا): خطوة تصدير مجدولة تنزّل نص المستند إلى لقطة محلية مختومة بالبصمة والوقت داخل مجلد عمل خط الأنابيب، ومنها يُستخرج `decisions.json`.
- الاستخراج الآلي من نص حرّ هشّ بطبيعته (ترقيم يدوي، أحدث قرار فوق): لذلك `extraction` يُوسم صراحة، وأي قرار لا يطابق نمطًا واضحًا يدخل قائمة «يحتاج تثبيتًا يدويًا» بدل تخمينه، وتُعرض القرارات دائمًا **برابط إلى المستند الأصلي** بوصفه المرجع عند أي شك. وحتى تستقر خطوة التصدير، البديل الآمن للمرحلة الأولى: `decisions.json` يُبنى من سجلات PGOS ‏Decision وقيود السجل من نوع decision (كلاهما ملفي وموثوق البنية) مع بطاقة بارزة تربط بسجل المقر الكامل — عرض ناقص معلن خير من استخراج صامت مخطئ.

### ٢.٥ المقارنة والحكم: كيف تصل البيانات إلى المتصفح؟

| المعيار | (أ) JSON ثابت وقت البناء/المزامنة | (ب) Supabase | (ج) API حي من المتصفح |
|---|---|---|---|
| التكلفة | **صفر** — استضافة ثابتة على Vercel ضمن نفس حساب المشاريع | صفر مبدئيًا (طبقة مجانية) لكن مشروعًا جديدًا يُدار ويُراقب سقفه | صفر ظاهريًا، وثمنه تعقيد ومفاتيح |
| الأمان | البيانات المنشورة هي المنشورة — تُضبط بالتنقية قبل التوليد + بوابة وصول (القسم ٣)؛ لا مفاتيح في المتصفح إطلاقًا | الأقوى بنيويًا: Auth + RLS كما في تطبيق المدرس، وبيانات لا تغادر القاعدة إلا لمستخدم مصرّح | **الأخطر:** مفاتيح Linear/Drive لا يمكن أن توجد في متصفح؛ وسيط خلفي إلزامي = مشروع ثانٍ كامل |

| الحداثة | بحداثة آخر مزامنة (ساعتين للـ Linear، ساعة للحارس) — **كافية**: هذه إيقاعات النظام الحالية نفسها، والمالك يقرأ صورًا دورية أصلًا | لحظية نظريًا، لكن الكاتب إليها مزامنة دورية أيضًا — فالحداثة الفعلية واحدة | لحظية حقيقية — لا قيمة لها هنا: لا قرار يُتخذ على بيانات أقدم/أحدث بدقائق في هذا النظام |
| الأعطال | آخر نسخة صالحة تبقى معروضة مع شارة قدم — تدهور رشيق | عطل القاعدة/المشروع = موقع فارغ | عطل أي مزوّد = ثقوب في الصفحة |
| قابلية التدقيق | كل نسخة مولّدة مختومة ببصمات مصادرها — إعادة إنتاج أي صفحة تاريخية ممكنة | يتطلب جهد لقطات إضافيًا | شبه مستحيلة |

> **الحكم: (أ) توليد JSON ثابت — هو خيار المرحلة الأولى والافتراضي الدائم ما لم يظهر مُشغّل تغيير موثق.**
> الأسباب الحاسمة: (١) صفر تكلفة وصفر بنية جديدة، انسجامًا مع انحراف D-2 نفسه الذي اختار الملفات على السيرفر؛ (٢) كل البيانات المطلوبة **موجودة أصلًا كملفات** في بيئة التشغيل — التحويل خطوة أخيرة لا نظام جديد؛ (٣) إيقاع حداثة النظام الحالي (ساعة/ساعتين) يجعل «اللحظي» ميزة وهمية هنا؛ (٤) لا مفتاح ولا سرّ واحد في المتصفح.
>
> **مُشغّلات إعادة النظر في (ب) Supabase** (تُسجّل كقرار عند حدوثها، لا تُستبق): حاجة كتابة من الموقع نفسه (اعتماد قرار/قيد جديد من الواجهة) · تعدد مستخدمين بصلاحيات مختلفة على مستوى الصفوف · حجم بيانات يتجاوز بضعة ميجابايتات من JSON · حاجة بحث/فلترة خادمية. عندها يُعاد استخدام نمط تطبيق المدرس حرفيًا (Auth + RLS + `api.ts`/`hooks.ts`) وتتحول ملفات JSON إلى بذرة استيراد.
> **(ج) مرفوض** لأي مرحلة متصفحية: يُقبل فقط لو تحوّل «الوسيط» إلى وظائف خادمية داخل مشروع Vercel نفسه بأسرار خادمية — وهو عندئذ ليس (ج) بل إعادة تصميم تُقيّم وحدها.

## ٣. حماية الوصول — بيانات شركة داخلية على موقع منشور

### ٣.١ تصنيف ما سيُعرض (من السجلات نفسها)

بيانات الموقع مصنفة **INTERNAL** (سجل PRJ-TOTO-001)، وبعض ما يخص تطبيق المدرس **CONFIDENTIAL** (سجل PRJ-TEACHER-001). المحتوى: قرارات شركة، حالة مشاريع، فجوات تشغيل، مخاطر — لا أسرار تقنية ولا بيانات عملاء ولا مفاتيح، لكنه **ليس للنشر العام**، ويرتبط بقاعدة ثابتة: **هوية مالك الشركة مجهولة على الصفحات العامة** — فالموقع يجب ألا يربط الشركة بشخص مالكها علنًا.

### ٣.٢ سلّم الحلول — من الأبسط إلى الأقوى

| المستوى | الحل | قوته الحقيقية | ملاحظات |
|---|---|---|---|
| ٠ | رابط غير مُعلن + `noindex` + اسم نطاق غامض | **ليست حماية** — أي رابط يتسرب يفتح كل شيء، وملفات JSON الثابتة تُجلب مباشرة | مقبول فقط لمعاينة مؤقتة ببيانات منقّاة/وهمية |
| ١ | كلمة سر داخل كود الواجهة (قفل JavaScript) | **ليست حماية** — البيانات موجودة في الملفات لمن يطلبها مباشرة؛ تُذكر صراحة كي لا تُعتمد وهميًا | مرفوض كحل وحيد لبيانات حقيقية |
| ٢ | **Vercel Deployment Protection / حماية بكلمة سر على مستوى المنصة** | حماية فعلية عند الحافة: الطلب يُرفض قبل وصول أي ملف | توفرها وشروطها (خطة/نوع حماية: معاينة فقط أم إنتاج أيضًا) **يُتحقق منها في لوحة Vercel لحظة الإعداد** — لا تُفترض من الذاكرة |
| ٣ | **هوية عند الحافة: Cloudflare Access (Zero Trust) أو ما يعادلها** أمام النطاق | قوية: دخول بحساب/بريد مصرّح + جلسة، بلا تغيير في كود الموقع؛ الطبقة المجانية تكفي فريقًا صغيرًا (يُتحقق من حدودها عند الإعداد) | تتطلب نطاقًا مخصصًا تحت إدارة Cloudflare؛ خطوة إعداد لمرة واحدة |
| ٤ | **Supabase Auth + RLS** داخل التطبيق (نمط تطبيق المدرس) | الأقوى تطبيقًا: مستخدمون وصلاحيات وصفوف — لكنها مشروطة بالانتقال إلى الخيار (ب) أصلًا | مرحلة لاحقة عند تحقق مُشغّلات ٢.٥ |
| ٥ | عدم النشر العام أصلًا: شبكة خاصة/VPN أو نشر داخلي فقط | الأقوى مطلقًا | يكسر هدف «المالك يراه من موبايله من أي مكان» بسهولة — مبالغة لحجم الفريق الحالي (مالك + وكلاء) |

### ٣.٣ التوصية للمرحلة الأولى

1. **لا إطلاق عام قبل بوابة وصول من المستوى ٢ فأعلى — متحقق منها فعليًا، لا مفترضة.** الترتيب العملي: جرّب حماية منصة Vercel أولًا (صفر كود)؛ إن لم تغطِّ الإنتاج على الخطة الحالية، فالمستوى ٣ (Cloudflare Access) هو الهدف — كلاهما قبل أول نشر ببيانات حقيقية.
2. **التنقية قبل التوليد (دفاع ثانٍ مستقل عن البوابة):** خط الأنابيب يستبعد/يختصر حقولًا لا تحتاجها الواجهة: البصمات الخام الطويلة (تُعرض نتيجة التحقق لا السلسلة)، أي بريد/معرّفات شخصية داخل أوصاف Linear الطويلة تُراجع بقائمة تنقية، وأوصاف البنود تُختصر افتراضيًا مع رابط البند الأصلي لمن يملك صلاحيته في Linear أصلًا.
3. **بيانات المعاينة الأولى منقّاة:** أول نشر تجريبي يكون بلقطة منقّاة يدويًا (أو بيانات اصطناعية بنفس البنية) حتى تُثبت البوابة — إثبات البوابة نفسها جزء من أدلة القبول (محاولة وصول بلا جلسة = رفض موثق بلقطة/سجل).
4. `robots.txt` بمنع الفهرسة + `noindex` على الصفحات — نظافة إضافية، لا تُحسب حماية.
5. لا اسم للمالك ولا رابط شخصي في الموقع — الهوية المعروضة هي هوية الشركة فقط (3A Automation / توتو / PGOS).

## ٤. خط أنابيب المزامنة المقترح

### ٤.١ الشكل العام

```
المصادر (لا تُلمس)                خط الأنابيب (Python stdlib)              الناتج            العرض
─────────────────────            ────────────────────────────────         ──────────        ─────────
ledger/company-ledger.jsonl ─┐
pgos/records/*.json ─────────┤   ١ جمع + بصمات SHA-256 للمصادر
guard/{state,alerts} + تشغيل ┤   ٢ تحقق: سلسلة السجل · روابط PGOS ·
  الحارس نفسه                 ├─▶   اكتمال الرباعية · تطابق صف-بصف Linear
linear-sync/payload.json ────┤   ٣ تحويل إلى نموذج العرض + تنقية
Drive HQ: سجل القرارات ──────┤   ٤ توليد JSON ذرّي (مجلد مؤقت ← استبدال)
COMPANY-REFERENCE.md ────────┤   ٥ manifest.json (بصمات + أختام قدم)
templates/*.md ──────────────┘   ٦ فشل أي تحقق = إبقاء آخر نسخة صالحة + شارة
                                          │
                                          └─▶ public/data/*.json ─▶ بناء Vite ─▶ Vercel
```

- **اللغة والأدوات:** Python بمكتبة قياسية فقط — نفس قرار `ledger.py` والحارس (صفر تبعيات جديدة، ويعمل في بيئة التشغيل الحالية حيث تعيش المصادر).
- **ذرّية التوليد:** يُكتب الناتج في مجلد مؤقت ويُستبدل كاملًا عند نجاح كل التحققات؛ فشل جزئي لا يترك موقعًا نصف محدّث.
- **إعادة استخدام لا إعادة كتابة:** خطوة التحقق تستدعي منطق `ledger.py verify` وتشغيل `completeness_check.py` القائمين (مع كاشهما وسلوكهما الموثق) — الحارس يبقى صاحب حساب الرباعية الوحيد، والموقع يعرض نتيجته.

### ٤.٢ المصادر: التكرار والعتبات

| المصدر | طريقة الجمع | التكرار المقترح | عتبة القدم (شارة «قديم») | عند تجاوزها/فشلها |
|---|---|---|---|---|
| سجل الشركة JSONL | قراءة ملف + `verify` إلزامي | مع كل تشغيل أنابيب + **عند كل `append` جديد** (ربط بخطوة القيد) | ٢٤ ساعة بلا تشغيل أنابيب ناجح | سلسلة مكسورة = **إيقاف نشر كامل** + تنبيه (كود خروج الحارس 2 هو النموذج) |
| سجلات PGOS | قراءة 8+ ملفات + تحقق روابط | مع كل تشغيل؛ تتغير نادرًا (بقرار/أمر شغل) | ٧ أيام | رابط مكسور = فشل توليد هذا القسم وتنبيه، لا سجل يتيم |
| حارس الاكتمال | تشغيل `completeness_check.py` + قراءة `state.json`/`alerts.jsonl` | **ساعة** (إيقاع الكرون القائم أصلًا) | ساعتان (تشغيلان فائتان) | يُعرض آخر لقطة مع شارة؛ فجوات «تعذّر تحقق» تبقى مميزة عن «فجوات مؤكدة» كما في منطق الحارس |
| Linear (payload) | قراءة `linear-sync/payload.json` كما هو — لا API جديد | **كل ساعتين** (مزامنة اللوحة القائمة نفسها) | ٣ ساعات (نفس عتبة الحارس للوحة) | بعد العتبة: حالات البنود تُوسم «غير متحقق منها» بدل عرضها كحقائق |
| قرارات Drive HQ | تصدير مجدول من بيئة التشغيل (أدوات Drive المتصلة) إلى لقطة محلية مختومة، ثم استخراج موسوم | **عند كل قرار جديد** (خطوة واعية بعد تسجيله في المقر) + مراجعة أسبوعية للبصمة | ٧ أيام أو اختلاف بصمة بلا تحديث | استخراج غير مؤكد = قائمة تثبيت يدوي؛ الرابط للمستند الأصلي ظاهر دائمًا |
| مرجع الشركة + الميثاق | تحويل Markdown وقت التوليد | عند تغيّر الملف (بصمته في manifest) | — (مرجع بطيء التغير) | اختلاف بصمة بلا توليد جديد يظهر في manifest |
| القوالب/التقارير | ملء القوالب من JSON المولّد نفسه | ساعة: مع كل تشغيل · يومي: نهاية اليوم · أسبوعي: نهاية الأسبوع | حسب نوع التقرير (ساعتان/يوم/أسبوع) | تقرير قديم يُوسم بفترة تغطيته صراحة |

### ٤.٣ قواعد تشغيل صارمة

1. **لا رقم بلا مصدر:** كل بطاقة/جدول في الموقع يُبنى من حقل في نموذج العرض، وكل ملف مولّد مختوم بمصادره وبصماتها في `manifest.json` — وشريط حداثة ظاهر في الواجهة يعرض `generatedAt` وأقدم مصدر، فلا تُقرأ صورة قديمة على أنها حية.
2. **آخر نسخة صالحة لا تُحذف أبدًا بفشل جديد** — الفشل يُعلن (تنبيه في قنوات النظام الحالية) ويُعرض الموجود مع شارته.
3. **النشر خطوة منفصلة عن التوليد:** التوليد الناجح لا يعني نشرًا تلقائيًا في المرحلة الأولى؛ النشر (بناء + رفع Vercel) يخضع لبوابات المدرس نفسها (بناء أخضر + مراجعة) حتى يستقر الإيقاع، ثم يُنظر في أتمتته.
4. **كاتب واحد لكل مصدر** (قاعدة النظام القائمة): الأنابيب قارئ فقط لكل المصادر — لا يكتب في السجل ولا Linear ولا Drive إطلاقًا.

## ٦. خطة مراحل مختصرة (للتنفيذ اللاحق — ليست جزءًا من هذه الوثيقة)

1. **م١ — هيكل وعرض ثابت:** سقالة بنفس مكدّس المدرس + ثيمه ومكوناته، وخط أنابيب يولّد JSON من السجل وPGOS وLinear والحارس، وبيانات معاينة منقّاة، وSPA fallback مُتحقق منه. لا قرارات Drive بعد (بطاقة رابط للمقر).
2. **م٢ — بوابة الوصول:** تفعيل مستوى ٢ أو ٣ + دليل رفض غير مصرّح + تنقية آلية كاملة، ثم أول نشر ببيانات حقيقية.
3. **م٣ — قرارات Drive:** خطوة التصدير والاستخراج الموسوم + قائمة التثبيت اليدوي في سير العمل.
4. **م٤ — تقارير دورية:** ملء القوالب الثلاثة من نفس JSON ونشرها في قسم التقارير بإيقاع ٤.٢.
5. **إعادة تقييم Supabase** فقط عند تحقق أحد مُشغّلات ٢.٥ — بقرار مسجل جديد.

## ٧. أسئلة مفتوحة للمنسّق/المالك (لا تحجب بدء م١)

- خطة Vercel الحالية: هل تغطي حماية الإنتاج (Deployment Protection على Production) أم معاينة فقط؟ — تُحسم بالتحقق في اللوحة، وقد ترفع Cloudflare Access للأولوية.
- نطاق مخصص للموقع (تحت إدارة Cloudflare؟) أم نطاق `vercel.app` فرعي في م١؟
- اعتماد تشغيل فاليديتورز PGOS الأصلية (AC-3) — قرار مالك قائم أصلًا، يبقى مفتوحًا بمعزل عن هذا المسار.
