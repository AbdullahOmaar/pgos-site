## ١. خريطة النظام كاملة

### ١.١ ما هو PGOS — وما ليس هو

PGOS ‏(Project Governance OS) نظام تشغيل حوكمة **قابل للنقل ومستقل عن أي مشروع**: يعرّف كيف يُصرَّح بالشغل ويُخطَّط ويُنفَّذ ويُتحقَّق منه ويُغيَّر ويُصدَر ويُتعلَّم منه. وهو صراحةً **لا** يعرّف: استراتيجية منتج أي مشروع، ولا قواعده المجالية (domain rules)، ولا مكدّسه التقني، ولا التزاماته التنظيمية. وهو إطار جديد قائم بذاته: لا يرث اعتمادات أو سياسات أو سجلات أو صلاحيات من أي مشروع سابق (AIBA أو MWOS أو Aureon أو Nuvio…).

مكوّناته المادية في الريبو:
- `docs/governance/` — المواثيق والسلطة والأدوار وأوامر الشغل والقرارات والتكامل مع الأدوات.
- `docs/security/` — المخاطر والهوية وتصنيف البيانات وخط الأمان الأساسي وأدلة أمان المزودين.
- `docs/release/` — بوابات الإصدار والتراجع والتحقق الحي وأدلة الجاهزية النهائية.
- `docs/architecture/` — معيار سجلات قرارات المعمارية (ADR) + تقييم أسس أوبن سورس مقترح.
- `templates/` — ٩ قوالب سجلات JSON قابلة للقراءة الآلية.
- `scripts/` — فاليديتوران بايثون بلا أي اعتماديات خارجية (Python 3.10+).
- `tests/` + `examples/` — اختبارات وحدة ومشاريع اصطناعية (لا بيانات حقيقية فيها إطلاقًا).

### ١.٢ نموذج السلطة ومصادر الحقيقة (Authority Model)

القاعدة الأولى: **لكل فئة معلومات مصدر كانوني واحد**، والباقي روابط/مراجع تشير إليه — لا نسخ صامتة.

| فئة المعلومات | السلطة الكانونية في PGOS الأصلي | المراجع التابعة |
|---|---|---|
| الرسالة والنطاق والنتائج والأولويات | ميثاق/قرار Notion المعتمد | مشروع/قضايا Linear ترجع إليه |
| الملكية والتبعيات وأوامر الشغل | سجلات Notion | مراجع المسؤول/المشروع في Linear |
| المعمارية والمعايير الهندسية | وثائق GitHub المقبولة وADRs | قرار Notion يربط للـ ADR |
| الكود وسجل الإصدارات | GitHub | قضايا Linear وأوامر Notion تربط للـ PR/commit |
| أدلة المراجعة وCI والاختبارات | أدلة المزود عند المراجعة الدقيقة (exact-head) | القبول في Notion يشير للمراجعة الدقيقة |
| الاعتمادات والاستثناءات | سجلات اعتماد/قرار Notion | Linear/GitHub تحمل أرقام المراجع فقط |
| النشر وحالة التشغيل | مزود التشغيل الفعلي | إصدار GitHub وأدلة Notion تربط إليه |
| مخطط قاعدة البيانات وحالة البيانات الحية | قاعدة البيانات/المزود المالك | هجرة GitHub وسجل تغيير Notion |

**قواعد اختيار المصدر:** (١) حدّد فئة المعلومات قبل اختيار المصدر. (٢) فضّل السلطة المعيّنة لا أحدث نسخة معدّلة. (٣) افحص حالة الاعتماد والمراجعة (revision) والمالك والطابع الزمني والإحلال الصريح (supersession). (٤) أي مادة DRAFT أو مقترحة أو منسوخة أو قديمة = غير سلطوية. (٥) حلّ أي تعارض جوهري يُسجَّل كسجل قرار مرقّم المراجعة. (٦) لو السلطة UNKNOWN أو CONFLICTED → يُحظر الفعل المترتب عليها.

**ممنوع النسخ الصامت (No silent mirroring):** القرارات تُحفظ مرة واحدة في المصدر الكانوني وتُربط بمعرّفاتها في غيره؛ حالة التنفيذ في Linear فقط؛ حقيقة التشغيل عند مزودها — ولا يُستعاض عن القبول الحي بـ CI أخضر أو HTTP 200. ويُمنع نسخ أسرار أو بيانات شخصية أو لوجات حساسة كاملة داخل سجلات الحوكمة. والأدلة «تفسد» (تصبح stale) متى تغيّر جوهريًا: الكوميت، الأرتيفاكت، الإعدادات، البيئة، نطاق الاختبار، نموذج الصلاحيات، أو القرار المصدر.

**عندنا (مصالحة موثقة — انحراف D-1 في ملف التبنّي):** الكانوني لقرارات الشركة ومواثيقها هو **مقر Drive المشترك** بدل Notion (هو ما يقرأه/يكتبه الطرفان فعليًا، وأدوات الوكلاء المتصلة هنا تشمل Drive لا Notion)، مع حفظ قصد PGOS كاملًا: مصدر واحد والباقي مرايا معلنة. التنفيذ = Linear، الكود/المعايير/الأدلة = GitHub + ملفات النظام المحلية، حالة الإنتاج = المزود الفعلي (Vercel/Supabase)، وسجل الشركة الجامع = JSONL بسلسلة تجزئة يحمل صيغ سجلات PGOS (انحراف D-2)، و`canonical_sources` تحمل مفتاح `drive_hq` إضافيًا بجانب الأربعة الأصلية (انحراف D-3).

### ١.٣ الهويات المنفصلة وقناة المالك

PGOS يفصل بصرامة بين **أربعة فاعلين (principals)** لا يجوز خلطهم:
1. **المالك البشري (Human Project Owner):** يقدّم قرارات النطاق والاعتمادات عبر قناة محادثة موثقة.
2. **وكيل/عامل الذكاء الاصطناعي (agent/worker runtime):** فاعل مستقل؛ هويته وتكليفه وإرساله وإقراره بالاستلام وتسليمه تحتاج أدلة مستقلة — رسالة مالك لا تثبت وجود عامل ولا إقراره.
3. **حساب الأداة المتصلة:** GitHub وNotion وLinear وقواعد البيانات بهويات مرتبطة مستقلة؛ تُتحقق هوية الحساب الفعلي وصلاحية كل عملية على حدة — سلطة المالك في الشات لا تمنح صلاحيات عند المزودين.
4. **فاعل التطبيق (application actor):** مستخدمو التطبيق المحكوم ومستأجروه — مصادقة وتفويض عند حدّ التطبيق من جهة السيرفر.

**قاعدة قناة المالك (DEC-PGOS-001):** يجوز للمشروع أن يربط مالكه البشري بقناة محادثة موثّقة عبر قرار كانوني؛ عندها يُعامل مرسِل الرسائل في تلك القناة المؤسَّسة كمالك المشروع للتعليمات والقرارات الحوارية، دون مطالبته بحساب PGOS أو كلمة سر أو توكن أو معرّف جلسة يدوي. لكن هذا **إسناد حواري (conversational attribution) فقط** — ليس توقيعًا تشفيريًا ولا معرّف جلسة مستقرًا يتحقق منه PGOS مستقلًا إلا لو أتاحته المنصة فعلًا. الحسابات المشتركة/الغامضة، والرسائل المنقولة بلا مصدر، وسياقات المشاريع المتعارضة، والقنوات غير المربوطة = UNKNOWN حتى تُحسم. ويُسجَّل القرار الحاكم ومصدر/تاريخ المحادثة المتاح.

**عندنا:** قناة المالك الموثقة = محادثة واتساب المؤسسة (DEC-TOTO-001 + اتفاق موثق في الذاكرة/الميثاق)، والمالك المساءل هو Aboudi.

### ١.٤ الأدوار ومصفوفة الاعتماد

الأدوار عند PGOS تصف **المساءلة لا الصلاحيات التلقائية** — التعيين في دور لا يمنح بذاته صلاحية دمج أو إنتاج أو مال أو تدمير أو تواصل خارجي:

| الدور | المسؤولية |
|---|---|
| Project Owner | النتائج والنطاق والأولوية وقبول المخاطر والاعتمادات الخاصة بأفعال بعينها |
| Project Master / Governance Lead | سلامة الحوكمة والتبعيات وتتبّع القرارات واتساق الأدوات |
| Delivery Lead | تنسيق الدفعات المعتمدة وتبعياتها |
| Implementer | تنفيذ أمر الشغل المُسند فقط، داخل حدود مساره وبيئته وانتهائه |
| Independent Verifier | تقييم أدلة القبول دون أن يكون المؤلف الوحيد للتغيير في الشغل عالي المخاطر |
| Release Authority | منح اعتماد إصدار منفصل |
| Security / Data Owner | مراجعة مخاطر الأمان والخصوصية والبيانات والوصول المنطبقة |

**فرض الصلاحيات:** كل قدرة تُربط بـ: الفاعل + معرّف أمر الشغل ومراجعته المعتمدة + الفعل المسموح + المورد/المسار/السجل + البيئة + النافذة الزمنية/الانتهاء + مرجع الاعتماد + الشروط المسبقة. الفرض يكون عند حدّ المزود/التطبيق. المبدأ: **المنع افتراضيًا (default deny) وأقل امتياز (least privilege)**. تعليمة مالك صالحة قد تنشئ قرارًا أو تصرّح بأمر شغل محدود؛ لا تمنح أبدًا تفويضًا شاملًا لنطاق غير معلن أو لأفعال A4.

**استثناء موثق (DEC-PGOS-003):** لحزمة وثائق حوكمة PGOS وحدها، يجوز أن تفي مراجعة ذاتية موثقة من Project Master/المحافظ على الريبو ببوابة مراجعة الوثائق — بشرط تحديد المرشح الدقيق والمسارات المتغيرة ومعايير المراجعة والنتائج/التصرفات والنتيجة. الاستثناء لا يلغي التحقق المستقل ولا مراجعة الأمان/الخصوصية ولا Release Authority للشغل عالي الأثر، ولا يبيح اعتماد المرء أفعالَه A4 بنفسه، وقواعد المزود المفروضة على PR تبقى سارية. واعتماد المالك للتبنّي يبقى منفصلًا عن المراجعة الذاتية.

**عندنا:** سلسلة الأدوار العملية في ميثاق «توتو»: صاحب القرار (Aboudi) ← المدير (شات واتساب) ← البنّاء (ميزو) ← مراجع/مستكشف. والاعتماد عندنا: تقني/تشغيلي داخل أمر شغل معتمد = تنفيذ مباشر؛ والمحفوظ للمالك دائمًا (فلوس، إطلاق عام، قرارات تجارية، اسم عام، خطوات لا رجعة فيها) = اعتماد خاص بالفعل نفسه — وهو ما يقابل A4 عند PGOS.

### ١.٥ مستويات الاستقلالية A0–A4 (مستويات صلاحية أمر الشغل)

تظهر المستويات في قالب أمر الشغل (`permission.level`) وفي الفاليديتور الأساسي كمقياس مرتب `A0 < A1 < A2 < A3 < A4`. **تنبيه أمانة مهم:** وثائق PGOS **لا تعرّف دلالة كل مستوى تعريفًا مستقلًا كاملًا** — المعروف نصيًا فقط هو:

| المستوى | ما هو موثق فعلًا في الريبو |
|---|---|
| A0 | الأدنى في المقياس؛ لا تعريف دلالي مستقل في الوثائق (يُقبل من الفاليديتور كقيمة صالحة فقط) |
| A1 | مثال القالب: أفعال قراءة (`read_project_docs`) على `docs/**` محليًا، و`approval_ref` = ‏`NOT_REQUIRED_FOR_A1` — أي قراءة/اطلاع لا تحتاج مرجع اعتماد |
| A2 | مثال المشروع الاصطناعي: `read_project_docs` + `edit_feature_code` + `run_local_tests` على مسارات ميزة محددة محليًا، بـ`approval_ref` يشير لقرار (DEC-SAMPLE-001) — أي تنفيذ محلي محدود داخل نطاق معتمد |
| A3 | فوق A2 ودون A4 في المقياس؛ لا تعريف دلالي مستقل في الوثائق |
| A4 | أعلى مستوى — **إلزامي** لأي فعل عالي الأثر، ويتطلب `approval_ref` حقيقيًا (خاصًا بالفعل نفسه)؛ الفاليديتور يرفض A4 بلا مرجع اعتماد أو بالمرجع الشكلي الخاص بـ A1 |

**الأفعال عالية الأثر** (قائمة الفاليديتور الحرفية `HIGH_IMPACT_ACTIONS`): ‏`merge_to_default`، ‏`production_deploy`، ‏`production_write`، ‏`destructive_migration`، ‏`sensitive_data_export`، ‏`financial_side_effect`، ‏`legal_side_effect`، ‏`paid_provisioning`، ‏`external_communication`. أي أمر شغل يتضمن فعلًا منها بمستوى أقل من A4 = خطأ فاليديشن.

### ١.٦ ميثاق المشروع ودورة حياة المشروع

قبل أي تخطيط تنفيذي، الميثاق (Charter) يعرّف الحد الأدنى من الهوية والقصد والمساءلة والقيود. حقول إلزامية: معرّف مشروع ثابت لا يتغير + اسم عرض؛ الراعي/المالك المساءل + قائد الحوكمة؛ بيان المشكلة والمستفيدون والنتائج المتوقعة؛ مقاييس نجاح قابلة للقياس؛ قدرات داخل النطاق و**لا-أهداف صريحة**؛ قيود (ميزانية، تواريخ، مكدّس، بائع، قانوني، بيانات، فريق، مستويات خدمة)؛ البيئات وتصنيف البيانات؛ طبقة المخاطر ومبررها؛ روابط المصادر الكانونية (Notion/Linear/GitHub/runtime) أو `NOT_APPLICABLE` صريحة؛ نسخة بروفايل PGOS والانحرافات المعتمدة؛ الحالة والمراجعة وتاريخ الإنشاء وتاريخ المراجعة.

**دورة حياة المشروع:**
`INTAKE → GOVERNANCE_SETUP → READY → ACTIVE → PAUSED / BLOCKED → RELEASE_CANDIDATE → RELEASED → MAINTENANCE → CLOSED`
وحالات استثنائية: `REJECTED`، ‏`CANCELLED`، ‏`ARCHIVED`.

المشروع لا يصير `READY` إلا بوجود: ميثاقه، ومالك مساءل، وحدود نطاق، وتصنيف مخاطر، وخريطة مصادر، وسير عمل تسليم، وحد أدنى من ضوابط الأمان، و**أول أمر شغل معتمد**. قائمة جاهزية من ٩ بنود (مالك وسلطة قرار مسمّيان؛ مشكلة ونتائج ومقاييس ونطاق ولا-أهداف مقبولة؛ تصنيف مخاطر وبيانات مكتمل؛ خريطة مصادر مكتملة؛ وصول أدوات وأدوار متحقق منها؛ خط أمان/خصوصية مختار؛ أول أمر شغل معتمد بمعايير قابلة للاختبار؛ مسار تحقق وإصدار محدد؛ فجوات واستثناءات معروفة مسجلة).

### ١.٧ دورة حياة أمر الشغل (Work Order)

أمر الشغل هو وحدة التصريح بالتنفيذ. حقوله الإلزامية (من المعيار والقالب معًا): المعرّف والمشروع والعنوان والمراجعة والحالة؛ الهدف/معرّف النتيجة وقيمته القابلة للقياس؛ النطاق واللا-أهداف الصريحة؛ المالك البشري المساءل + مصدر تعليمة المالك/مرجع قرارها + قائد التسليم + هوية مُسند إليه **متحقق منها**؛ هوية عامل التشغيل منفصلة بدليل ربطها (لا تُستنتج من محادثة المالك)؛ منحة الصلاحية (مستوى الاستقلالية، الأدوات، الأفعال، الموارد، البيئة، الانتهاء)؛ فاعل الأداة المتصلة ودليل صلاحية العملية عند الاقتضاء؛ التبعيات ومعرّفات القرارات المسبقة؛ معايير قبول قابلة للقياس وسلوك سلبي/فشل؛ خطة تحقق ومتحقق ومصدر أدلة؛ مستوى المخاطر وأثر الأمان/الخصوصية/البيانات؛ تراجع أو فعل تعويضي عند الاقتضاء؛ حدود ميزانية/جهد عند الانطباق؛ مرجع الاعتماد ووقت الإنشاء وسجل التغييرات.

**دورة الحياة:**
`DRAFT → SUBMITTED → APPROVED → ASSIGNED → CLAIMED → IN_PROGRESS → SUBMITTED_FOR_REVIEW → VERIFYING → ACCEPTED → CLOSED`
وحالات استثنائية: `BLOCKED`، ‏`WAITING_APPROVAL`، ‏`PAUSED`، ‏`REWORK`، ‏`REJECTED`، ‏`CANCELLED`، ‏`EXPIRED`.

قاعدة فصل صارمة يكررها PGOS: **الاعتماد ≠ الإسناد ≠ الإرسال (dispatch) ≠ الإقرار بالاستلام ≠ التقديم ≠ القبول** — كل خطوة حالة مستقلة بدليلها. واكتمال قضية Linear أو دمج PR ليس بذاته قبول نتيجة ولا تحقق نشر.

**التفكيك (Decomposition):** ‏Project Goal ← Outcome ← Batch ← Work Order ← Linear Issue(s) ← GitHub Change(s) ← Verification Evidence. التجميع حول نتائج متماسكة؛ مالك مساءل واحد وكاتب أساسي واحد لكل حدّ مشترك؛ وتُعرَّف الواجهات والتبعيات قبل أي تنفيذ متوازٍ.

**ربط الأدوات:** Notion كانوني للميثاق والنتائج والنطاق والأولويات والملكية والتبعيات وأوامر الشغل والقرارات والاعتمادات والمخاطر والاستثناءات والقبول والتسليمات (سجل كانوني واحد لكل فئة سجل وبمعرّفات ثابتة). Linear للتنفيذ فقط: Initiative (برنامج اختياري) ← Project (برنامج تسليم محدود) ← Milestone (نقطة نتيجة/إصدار) ← Issue (أمر شغل معتمد أو وحدة تنفيذ) ← Sub-issue (وحدة مملوكة/قابلة للتحقق منفصلة) ← Cycle (نافذة سعة، **ليست** اعتماد نطاق). كل قضية تربط: Project ID + Outcome ID + Work Order ID + مراجع القرارات + المصدر الكانوني + PR/commit عند الانطباق — وحالة Linear لا تعني أبدًا اعتماد مالك أو إذن إصدار. GitHub: ‏`AGENTS.md` وREADME و`docs/architecture` و`docs/adr` و`docs/security` وrunbooks وقوالب قضايا/PR واختبارات وسكربتات؛ وإعدادات حماية الفروع ومراجعة PR الإلزامية وفحوصات exact-head المطلوبة ومسح الأسرار وبيئات النشر تُضبط في إعدادات المزود — **الوثائق وحدها لا تفرض شيئًا**.

### ١.٨ القرارات وضبط التغيير والاعتمادات

كل قرار جوهري يحمل: Decision ID + Project ID + عنوان + حالة + مراجعة + سياق + خيارات (**منها «لا تفعل شيئًا» دائمًا**) + الخيار المختار ومبرره + العواقب + النطاق/العقود/الأنظمة المتأثرة + المخاطر + مالك القرار + المعتمِدون + مراجع مستقل عند الحاجة + النسخة الفعالة + تاريخ مراجعة + روابط الإحلال (supersession).

**حالات القرار/طلب التغيير:** ‏`PROPOSED`، ‏`UNDER_REVIEW`، ‏`APPROVED`، ‏`REJECTED`، ‏`DEFERRED`، ‏`SUPERSEDED`، ‏`REVOKED` (وطلب التغيير يضيف `CANCELLED`).

**مصدر الاعتماد (Approval provenance):** الاعتماد يجب أن يكون صريحًا ومنسوبًا ومحدد النطاق وخاصًا بالنسخة. يُسجَّل المرجع الكانوني للقرار/أمر الشغل، ومع قناة مالك مربوطة: مصدر/تاريخ محادثة المالك والنطاق الدقيق المعتمد. **لا يُستنتج اعتماد أبدًا** من صمت أو تسميات حالة أو إسناد قضية أو اعتماد سابق غير ذي صلة. الاعتماد يحدد الفعل والمورد والبيئة والنطاق ونافذة الصلاحية بدقة.

**فئات التغيير وضوابطها الدنيا:**

| الفئة | أمثلة | الحد الأدنى للضبط |
|---|---|---|
| Editorial | خطأ إملائي/تنسيق بلا تغيير معنوي | مراجعة محافظ |
| Minor | سلوك منخفض المخاطر متوافق خلفيًا | أمر شغل + اختبار/مراجعة ذات صلة |
| Major | نطاق أو API أو مخطط أو معمارية أو وصول أو تغيير كاسر | قرار + تحليل أثر + هجرة/تراجع + اعتماد مالك |
| High impact | إنتاج أو خصوصية/أمان أو مالي/قانوني أو أثر لا رجعة فيه | اعتماد خاص بالفعل + تحقق مستقل + ضوابط إصدار |

تغييرات السياسات المضبوطة/الأمنية/المعمارية تتطلب عادة مراجعة غير المؤلف واعتماد مالك صريح قبل التبنّي، ما لم يوجد قرار كانوني بنطاق محدد يقرر طريقة مراجعة بديلة (وهو موضع استثناء DEC-PGOS-003 المحدود أعلاه).

**معيار ADR:** سجل واحد لكل قرار معماري جوهري، يُحفظ مقبولًا في ريبو المشروع المحكوم ويُربط بسجل الحوكمة/الاعتماد. ١٠ أقسام إلزامية: معرّف وعنوان ومشروع ونسخة وحالة (`PROPOSED/ACCEPTED/SUPERSEDED/REJECTED`)؛ سياق ودوافع؛ قيود وسمات جودة؛ خيارات (منها عدم الفعل)؛ قرار ومبرر؛ عواقب ومفاضلات ومخاطر؛ أثر أمان/خصوصية/بيانات/تشغيل؛ هجرة وتوافق وتراجع؛ معتمِدون ومعرّف قرار مرتبط؛ يحل محل/يُحل محله. وADR بحالة ACCEPTED لا يمنح بذاته إذن تنفيذ أو إنتاج أو إصدار.

### ١.٩ المخاطر والأمان والبيانات

**تسجيل المخاطر:** الاحتمالية والأثر كلٌّ من ١–٥، والدرجة الكامنة = الاحتمالية × الأثر. النطاقات المقترحة: ١–٤ LOW، ‏٥–٩ MODERATE، ‏١٠–١٦ HIGH، ‏١٧–٢٥ CRITICAL. وأي أثر قانوني/سلامة/أمان/خصوصية/مالي/لا رجعة فيه قد يفرض طبقة أعلى بغض النظر عن الحساب.

**طبقات مخاطر المشروع (دليل التبنّي):** ‏LOW = شغل قابل للعكس منخفض الأثر غير حساس؛ MODERATE = سلوك ظاهر للمستخدم وتكاملات وتغييرات بيانات غير حساسة؛ HIGH = مصادقة أو تفويض أو بيانات شخصية أو بنية حرجة أو مال أو التزامات قانونية أو كتابات إنتاج أو آثار لا رجعة فيها. يجوز للمشروع تشديد الضوابط؛ **لا يجوز إضعاف ضابط إلزامي عالي المخاطر بصمت**.

**تصنيف البيانات:**

| الطبقة | أمثلة | التعامل |
|---|---|---|
| PUBLIC | مواد منشورة | سلامة ونسبة |
| INTERNAL | خطط ومقاييس داخلية غير حساسة | وصول مشروع مصرح |
| CONFIDENTIAL | سجلات عملاء، شروط تجارية، بيانات موظفين خاصة | على قدر الحاجة، تقليل، مشاركة مضبوطة |
| RESTRICTED | بيانات اعتماد وأسرار وبيانات شخصية/مالية/صحية شديدة الحساسية | أنظمة آمنة مخصصة؛ لا تُلصق أبدًا في وثائق مشروع عامة |

PGOS **لا يدّعي أي شهادة امتثال**؛ كل مشروع يربط التزاماته القانونية/التنظيمية المنطبقة بنفسه. (عندنا: مخاطر مشروع توتو MODERATE وبياناته INTERNAL — ملف التبنّي §٤.)

**خط الأمان الأساسي:** تحقق من الهوية والتفويض من جهة السيرفر عند كل حدّ محمي؛ منع افتراضي وأقل امتياز وفصل مشروع/مستأجر/بيئة/بيانات؛ أسرار في مديري أسرار معتمدين فقط (أبدًا في Notion أو Linear أو كود أو لوجات)؛ كل مدخل مستخدم ومخرجات AI ووثائق مسترجعة وملفات وتعليقات وتعليمات خارجية = **غير موثوقة**؛ تحقق من المدخلات وترميز المخرجات ومراجعة مخاطر التبعيات/سلسلة التوريد؛ تقليل البيانات الشخصية في العينات واللوجات ولقطات الشاشة والأدلة؛ اختبار المسارات المسموحة والممنوعة والعزل وغياب الآثار الجانبية غير المقصودة.

**بوابة تغيير الإنتاج/البيانات:** قبل أي كتابة إنتاج أو نشر أو هجرة أو فعل تدميري أو توفير مدفوع أو أثر جانبي خارجي: اعتماد خاص بالفعل + تحقق من الهدف + دليل نسخ احتياطي/استعادة أو تراجع + تحليل أثر + معالجة عدم تكرار/فشل (idempotency) + مراقبة + تحقق مستقل عند ارتفاع المخاطر + تحقق حي بعد الفعل.

**سياسة أمان الريبو (`SECURITY.md`):** الريبو عام حاليًا؛ لا تُنشر بيانات اعتماد أو بيانات شخصية أو سجلات عملاء أو حمولات استغلال بأهداف حية في قضايا عامة؛ الإبلاغ عن ثغرة يكون لمالك الريبو عبر قناة خاصة معتمدة مع النسخة/المراجعة المتأثرة والأثر وخطوات إعادة إنتاج آمنة وتخفيفات — بلا أي SLA ضمني في هذه المسودة.

### ١.١٠ الأدلة والإصدار والإغلاق

**حزمة مرشح الإصدار (Release Candidate packet):** مراجعة مصدر دقيقة وبصمة أرتيفاكت؛ نطاق معتمد ونسخ قرارات؛ فحوصات آلية/يدوية مطلوبة بنتائج من مجموعة `PASS / FAIL / NOT_RUN / STALE / UNKNOWN` فقط؛ تصرف المراجعة المنطبق (بما فيه المراجعة الذاتية الموثقة حيث ينطبق DEC-PGOS-003 فقط)؛ مراجعة أمان/خصوصية/هجرة بيانات؛ مشاكل معروفة ومخاطر متبقية واستثناءات معتمدة؛ خطة نسخ/تراجع/استعادة؛ اعتماد Release Authority مسمّى؛ إيصال نشر وتحقق وظيفي حي. و`READY_FOR_APPROVAL` **ليست** إذن نشر.

**جودة الدليل:** كل عنصر دليل يعرّف: Evidence ID + المشروع/أمر الشغل + المعيار + رابط المصدر + مراجعة الكوميت/الأرتيفاكت/المخطط الدقيقة + البيئة + الإعدادات ونطاق الاختبار + الأمر/الإجراء + النتيجة + الطابع الزمني + المنتج + المراجع + مسببات الإبطال (invalidation triggers).

**حالات إتمام متميزة — لا يجوز دمجها أبدًا:**

| الحالة | معناها |
|---|---|
| IMPLEMENTED | التغيير موجود |
| TESTED | الفحوصات المطلوبة نجحت على المرشح الدقيق ذي الصلة |
| REVIEWED | المراجعة المطلوبة قبلت ذلك المرشح |
| ACCEPTED | مالك النتيجة/المتحقق قبل المعايير |
| MERGED | دُمج في الفرع الهدف |
| DEPLOYED | المزود يفيد بنشر الأرتيفاكت |
| LIVE_VERIFIED | البيئة/السلوك الحي المقصود فُحص فعلًا |

نجاح بناء ليس قبول منتج، وHTTP 200 ليس تحقق رحلة مستخدم.

### ١.١١ تقييم الأسس الأوبن سورس (مقترح فقط — ليس قرارًا)

وثيقة `open-source-foundation-evaluation.md` بحالة **PROPOSED / DRAFT — تقييم فقط**: لا تختار ولا تعتمد أي مكوّن إنتاجي، ولا تصرّح بتركيب أو توفير أو هجرة أو تكامل إنتاجي أو دفع أو استبدال نموذج السلطة الحالي. خلاصتها المحمولة للأمام: إبقاء ترتيب Notion + Linear + GitHub؛ تقييم **OPA** كمكوّن قرار سياسات (PDP) على أن تبني PGOS مصادقتها وفرضها (PEP) بنفسها — OPA لا يصادق هوية ولا يفرض شيئًا وحده؛ مقارنة **Conductor OSS** (مرشح A) و**Temporal** (مرشح B) و**Flowable OSS** (مرشح C) على سير عمل اصطناعي واحد ببطاقة تقييم من ١٠ محاور (متانة أثناء انتظار اعتماد، رفض عند حدّ الفرض لهوية مجهولة/منتهية/عابرة للمشاريع/مراجعة خاطئة، أثر تدقيقي، عدم تكرار، ترقية نسخ نشطة، تكاملات، OIDC وأقل امتياز، بصمة تشغيل، ترخيص وصيانة)؛ OpenProject بديل إدارة مشاريع فقط بلا هجرة من Linear؛ و**Kestra OSS مرفوض** كحدّ هوية/اعتماد أساسي لأن نسخته المجانية بحساب Basic Auth مشترك واحد. وأي POC قابل للتشغيل يحتاج أمر شغل محدودًا مستقلًا — وهوية جلسة المساعد الحالية فيه NOT VERIFIED.

## ٢. أنواع السجلات وحقولها الأساسية

تسعة أنواع سجلات JSON، لكل منها قالب في `templates/` ومعرّف ببادئة ثابتة وسجل `record_type`. ستة أنواع يغطيها الفاليديتور الأساسي، وثلاثة يغطيها الموسّع. الحقول أدناه هي **الإلزامية** كما يفرضها الفاليديتوران والقوالب (القوالب والأمثلة تحمل حقولًا إضافية اختيارية مذكورة حيث تهم).

| النوع (البادئة) | الغرض | الحقول الأساسية الإلزامية | الحالات |
|---|---|---|---|
| **Project** ‏(PRJ-) | ميثاق المشروع وهويته | `id`, `name`, `revision`, `status`, `owner{id, verified}`, `problem`, `outcomes` (غير فارغة), `scope` (غير فارغة), `non_goals`, `risk_tier`, `data_classes`, `canonical_sources{notion, linear, github, runtime}` — واختياريًا `created_at`, `review_date`, `success_metrics`, `governance_profile_version`, `approved_deviations` | دورة حياة المشروع §١.٦ (من GOVERNANCE_SETUP إلى CLOSED + استثنائية) |
| **WorkOrder** ‏(WO-) | وحدة التصريح بالتنفيذ | `id`, `project_id`, `revision`, `title`, `status`, `objective`, `scope`, `non_goals`, `owner_id`, `assignee{id, verified}`, `permission{level A0–A4, actions, resources, environment, expires_at, approval_ref}`, `acceptance_criteria[{id, given, when, then, evidence_required}]`, `verification_plan`, `risk_tier` | دورة §١.٧ (DRAFT…CLOSED + استثنائية) |
| **Decision** ‏(DEC-) | قرار جوهري قابل للتتبع والإحلال | `id`, `project_id`, `revision`, `title`, `status`, `context`, `options`, `decision`, `rationale`, `owner_id`, `approver_ids` — وإضافات القالب/المثال: `effective_at`, `consequences`, `risk_refs`, `review_date`, `supersedes` | PROPOSED, UNDER_REVIEW, APPROVED, REJECTED, DEFERRED, SUPERSEDED, REVOKED |
| **Risk** ‏(RSK-) | خطر مسجل بدرجة محسوبة | `id`, `project_id`, `title`, `description`, `likelihood` ‏(١–٥), `impact` ‏(١–٥), `inherent_score` (= حاصل ضربهما), `mitigations`, `owner_id`, `status` — واختياري `residual_score` ‏(١–٢٥) | OPEN (في القالب/الفاليديتور؛ الوثائق لا تحصي حالات مغلقة بدقة) |
| **Evidence** ‏(EVD-) | دليل تحقق مرتبط بمعيار ومراجعة دقيقة | `id`, `project_id`, `work_order_id`, `criterion_ids` (غير فارغة), `exact_revision`, `environment`, `scope`, `procedure`, `result`, `producer_id`, `timestamp` — وإضافات المثال: `source_url`, `reviewer_id`, `invalidation_triggers` | النتيجة فقط: PASS, FAIL, NOT_RUN, STALE, UNKNOWN |
| **Release** ‏(REL-) | إصدار وبواباته | `id`, `project_id`, `work_order_ids`, `status`, `exact_revision`, `environment`, `checks[{id, result}]`, `rollback_plan`, `release_authority_id` — وشرطيًا `approval_ref`, ولـ LIVE_VERIFIED: ‏`deployment_receipt` + `live_verification` | NOT_READY, READY_FOR_APPROVAL, APPROVED, DEPLOYING, DEPLOYED, LIVE_VERIFIED, ROLLED_BACK, FAILED |
| **ChangeRequest** ‏(CHG-) — موسّع | طلب تغيير بتحليل أثر شامل | كل حقول WorkOrder الهوياتية + `trigger`, `reason`, `current_state`, `proposed_state`, وأ impacts: ‏`scope/timeline/budget/technical/data/security/privacy`, ‏`migration_plan`, `compatibility_plan`, `rollback_plan`, `test_evidence_impact`, `risk_classification` ‏(LOW–CRITICAL), `required_approvers` — وشرطيًا `decision_ref`, `expires_at`, `effective_version`, `follow_up` | PROPOSED, UNDER_REVIEW, APPROVED, REJECTED, DEFERRED, SUPERSEDED, CANCELLED |
| **Handoff** ‏(HOF-) — موسّع | تسليم بين فاعلَين بأدلة | `id`, `project_id`, `work_order_id`, `revision`, `status`, `from_identity{id, verified}`, `to_identity{id, verified}`, `scope_summary`, `acceptance_status`, `branch`, `base_sha`, `head_sha`, `changed_files[]`, `tests[]`, `review_ci_runtime_evidence[]`, `not_run_checks[]`, `blockers[]`, `remaining_work[]`, `next_action`, `created_at` — وروابط notion/linear/github اختيارية | DRAFT, PREPARED, SUBMITTED, ACKNOWLEDGED, ACCEPTED, REJECTED, BLOCKED |
| **Incident** ‏(INC-) — موسّع | حادث بخط زمني منضبط | `id`, `project_id`, `revision`, `severity`, `status`, `start_at`, `detected_at`, `affected_scope[]`, `affected_data[]` (قيم تصنيف البيانات فقط), `detection`, `impact`, `containment`, `recovery`, `owner_id` — وشرطيًا `contained_at`, `resolved_at`, `root_cause`, `evidence_refs`, `follow_up_actions` | الخطورة: LOW, MODERATE, HIGH, CRITICAL · الحالة: OPEN, INVESTIGATING, CONTAINED, RESOLVED, CLOSED |

قواعد هوية عامة لكل السجلات: `id` معرّف ثابت كبير الأحرف يطابق النمط `^[A-Z][A-Z0-9-]{2,63}$`، و`revision` عدد صحيح موجب، وكل سجل (عدا Project نفسه) يرتبط بـ `project_id` يجب أن يحلّ إلى مشروع موجود.

## ٣. الفاليديتورز — ما يفعلانه وما لا يفعلانه

### ٣.١ الفاليديتور الأساسي — `scripts/validate_records.py`

سكربت بايثون بلا اعتماديات، يُشغَّل على مجلد (`python scripts/validate_records.py <dir>`) فيقرأ كل `*.json` فيه تكراريًا. كود خروج: 0 نجاح، 1 نتائج، 2 مجلد غير موجود. يطبع عند النجاح صراحة: «structural and cross-reference checks only».

**يفحص لكل سجل:**
- أنه كائن JSON وأن `record_type` من الأنواع الستة المدعومة، ووجود كل حقل إلزامي غير فارغ (حسب جدول REQUIRED في الكود).
- صيغة `id` وكون `revision` عددًا صحيحًا موجبًا، وصلاحية `risk_tier` إن وُجد.
- **Project:** ‏owner فيه id و`verified` منطقي؛ outcomes وscope قوائم غير فارغة؛ non_goals قائمة؛ data_classes ضمن الأربع طبقات؛ canonical_sources فيها المفاتيح الأربعة (notion/linear/github/runtime) كنصوص غير فارغة؛ صيغ `created_at` ‏(ISO-8601) و`review_date` ‏(YYYY-MM-DD) إن وُجدا.
- **WorkOrder:** ‏assignee به id وverified منطقي؛ permission كائن بمستوى ضمن A0–A4، أفعال نصية غير فارغة، موارد غير فارغة، بيئة موجودة، `expires_at` بصيغة ISO-8601 **وغير منتهٍ فعليًا وقت الفحص**؛ أي فعل عالي الأثر (§١.٥) يتطلب A4؛ وA4 يتطلب approval_ref حقيقيًا؛ acceptance_criteria غير فارغة وكل معيار مكتمل الحقول الخمسة (id/given/when/then/evidence_required)؛ وحالة APPROVED تتطلب approval_ref + assignee متحققًا منه (`verified: true`).
- **Decision:** ‏حالة APPROVED تتطلب decision غير فارغ ومعتمِدًا واحدًا على الأقل؛ و`effective_at` إما ISO-8601 أو null.
- **Risk:** ‏likelihood وimpact بين ١ و٥، و`inherent_score` يساوي حاصل ضربهما بالضبط، و`residual_score` إن وُجد بين ١ و٢٥.
- **Evidence:** ‏result ضمن الخمس قيم، criterion_ids غير فارغة، timestamp بصيغة ISO-8601، exact_revision نص غير فارغ.
- **Release:** ‏status ضمن الثماني حالات؛ الحالات من APPROVED فأعلى تتطلب approval_ref؛ وLIVE_VERIFIED يتطلب deployment_receipt وlive_verification؛ وchecks قائمة.

**يفحص عبر السجلات (cross-reference):** عدم تكرار أي `id` في المجلد كله؛ كل `project_id` في WorkOrder/Decision/Risk/Evidence/Release يحلّ إلى Project موجود في نفس المجموعة؛ Evidence يرتبط بـ WorkOrder موجود **ومن نفس المشروع**؛ وكل WorkOrder في Release موجود ومن نفس المشروع.

### ٣.٢ الفاليديتور الموسّع — `scripts/extended_records.py`

وحدة/CLI (`python -m scripts.extended_records <dir>`) للأنواع الثلاثة الإضافية، تقبل ملفات JSON فيها كائن واحد أو **مصفوفة كائنات**. يفحص:

- **مشترك:** الحقول الإلزامية لكل نوع، صيغة id وrevision، وproject_id غير فارغ.
- **ChangeRequest:** ‏status ضمن السبع حالات، risk_classification ضمن LOW–CRITICAL، required_approvers قائمة؛ وحالة APPROVED تتطلب decision_ref + معتمِدين غير فارغين؛ و`expires_at` إما null أو ISO-8601 **واعٍ للمنطقة الزمنية**.
- **Handoff:** ‏status ضمن السبع حالات؛ الهويتان فيهما id وverified منطقي؛ القوائم الست (changed_files/tests/review_ci_runtime_evidence/not_run_checks/blockers/remaining_work) قوائم فعلًا؛ `created_at` ISO-8601 واعٍ للمنطقة الزمنية؛ وحالة ACCEPTED تشترط تراكمًا: هويتان متحقق منهما + tests وأدلة مراجعة/CI غير فارغة + base_sha وhead_sha بصيغة SHA-1/SHA-256 كاملة (٤٠ أو ٦٤ حرفًا سداسيًا) + acceptance_status ∈ ‏{ACCEPTED, VERIFIED_COMPLETE} + **خلوّ** not_run_checks وblockers.
- **Incident:** ‏severity وstatus ضمن مجموعتيهما؛ affected_scope/affected_data قوائم وقيم affected_data ضمن طبقات التصنيف الأربع؛ start_at/detected_at إلزاميًا ISO-8601 واعية للمنطقة الزمنية؛ **انضباط الخط الزمني**: detected_at ≥ start_at، وcontained_at ≥ detected_at، وresolved_at ≥ contained_at؛ الحالات CONTAINED/RESOLVED/CLOSED تتطلب contained_at؛ والحالتان RESOLVED/CLOSED تتطلبان resolved_at وrecovery وroot_cause.
- **عبر مجموعة مختلطة (`validate_records`):** كشف ids مكررة؛ كل سجل موسّع يحلّ project_id إلى Project موجود — وإن غاب سجل المشروع أصلًا فالمجموعة كلها خطأ («record set must include its Project record»)؛ Handoff يحلّ work_order_id ومن نفس المشروع؛ وdecision_ref في ChangeRequest (إن وُجد) يحلّ إلى Decision موجود؛ وحتى أوامر الشغل الأساسية في المجموعة تُفحص مراجع مشاريعها.

ملف `scripts/__init__.py` مجرد docstring تعريفي للحزمة («PGOS governance validation package») بلا منطق.

### ٣.٣ ما لا يفعله أيٌّ منهما — بتصريح الريبو نفسه

من docstring السكربتين وREADME وSECURITY.md حرفيًا في المعنى: الفاليديتورز **فحص بنية وثوابت مختارة وروابط عابرة فقط**. هي ليست: محرك سياسات (policy engine)، ولا مزود هوية، ولا بوابة ضبط وصول، ولا متحقق توقيع تشفيري، ولا دليلًا على إعدادات أدوات. وبالتالي:

- سجل موسوم `APPROVED` مجرد **ادعاء** ما لم يكن مرجع اعتماده قابلًا للتحقق في نظام الاعتماد الكانوني للمشروع.
- فحص أعلام `verified` في التسليمات واتساق حالات الاعتماد هو فحص **بيانات سجل** فقط — لا يصادق على الفاعلين المسمّين ولا على المؤلف البشري لتعليمة شات.
- حماية الفروع والفحوصات المطلوبة ومسح الأسرار والصلاحيات وبوابات النشر يجب ضبطها واختبارها **عند المزود** نفسه.
- لا يفحص أيٌّ منهما: صحة روابط URL، وجود حسابات/أشخاص فعليين، صلاحية نطاق أمر شغل معنويًا، كفاية معايير القبول، أو أي سلوك تشغيلي وقت التنفيذ.

## ٦. ماذا يعني كل هذا عمليًا لتصميم موقع PGOS

الموقع هو «المكان الواحد» الذي يرى منه المالك الشركة (قرار مالك 2026-11-22 ~02:58: حوكمة + تاسكات + قرارات + سجل + تقارير + حالة بروجكتات، باحترافية تطبيق المدرس، ويحل محل اللوحة كواجهة أساسية **بعد** إطلاقه فقط). PGOS يملي على الموقع بنيته وقواعده:

### ٦.١ مبادئ تصميم مستمدة من PGOS نفسه (غير قابلة للتفاوض)

1. **الموقع مرآة قراءة لا مصدر حقيقة موازٍ:** لكل فئة معلومات مصدرها الكانوني (Drive HQ للقرارات، Linear للتنفيذ، GitHub للكود/الأدلة، المزود لحالة الإنتاج، JSONL لسجل الشركة). كل عنصر معروض يحمل رابط مصدره الكانوني ومعرّفه الثابت — تطبيقًا لقاعدة «لا نسخ صامت».
2. **الحالات لا تُدمج أبدًا:** واجهة الموقع تستخدم مفردات PGOS بدقة — IMPLEMENTED ≠ TESTED ≠ REVIEWED ≠ ACCEPTED ≠ MERGED ≠ DEPLOYED ≠ LIVE_VERIFIED، ونتائج الأدلة من الخمس قيم فقط (PASS/FAIL/NOT_RUN/STALE/UNKNOWN) بما فيها عرض NOT_RUN وSTALE بأمانة بدل إخفائها.
3. **كل اعتماد معروض مربوط بمرجعه:** لأن «APPROVED» في سجل ادعاء بلا مرجع قابل للتحقق، بطاقة أي قرار/أمر شغل/إصدار في الموقع تعرض `approval_ref` وتربطه بمصدره الكانوني.
4. **البيانات المعروضة INTERNAL:** سجلات الشركة مصنفة INTERNAL — الموقع نفسه يخضع لبوابة الإنتاج/البيانات (اعتماد خاص بالفعل قبل أي نشر) ولخط الأمان الأساسي (مصادقة عند الحدّ، أقل امتياز) قبل أن يكون واجهة عامة.
5. **الانحرافات معلنة لا مخفية:** D-1/D-2/D-3 وحالة «DRAFT معتمد لنطاق توتو» وفجوات §٥ تظهر في الموقع كما هي — الحوكمة القوية من البداية شرط المالك الصلب.

| قسم الموقع المقترح | مكوّن PGOS المقابل | المحتوى والمصدر الكانوني |

| **الرئيسية — صورة الشركة** | حالات المشاريع (§١.٦) + حالات الإتمام المتميزة (§١.١٠) | بطاقات المشاريع بحالات دورة حياتها، ما هو LIVE_VERIFIED فعلًا مقابل ما هو مجرد IMPLEMENTED، وتنبيهات حارس الاكتمال — مصادر: Linear + سجل الشركة + أدلة الإصدار |
| **المشاريع ومواثيقها** | سجل Project + معيار الميثاق والجاهزية (§١.٦) | بطاقة ميثاق لكل مشروع: نتائج ونطاق ولا-أهداف ومقاييس نجاح وطبقة مخاطر وتصنيف بيانات وخريطة مصادر، وقائمة جاهزية ٩ بنود بحالتها |
| **أوامر الشغل** | سجل WorkOrder + دورة حياته (§١.٧) | لوحة بحالات العشر + الاستثنائية، بطاقة أمر تعرض: النطاق واللا-أهداف، منحة الصلاحية كاملة (مستوى A + أفعال + موارد + بيئة + انتهاء)، المسند إليه وحالة تحققه، معايير القبول بصيغة given/when/then، وروابط قضايا Linear وتغييرات GitHub التابعة (سلسلة التفكيك كاملة) |
| **القرارات والتغييرات** | سجلّا Decision وChangeRequest + ضبط التغيير (§١.٨) | سجل قرارات بحالاته السبع وروابط الإحلال (من حلّ محل من)، وطلبات تغيير بتحليل أثرها الـ ١٠ أبعاد وفئتها (Editorial/Minor/Major/High impact) ومرجع قرار اعتمادها |
| **المخاطر** | سجل Risk + تسجيل المخاطر (§١.٩) | خريطة حرارة احتمال × أثر (١–٥)، الدرجة الكامنة والمتبقية، التخفيفات والمالك وحالة كل خطر — عندنا تبدأ بـ RSK-TOTO-001/002 |
| **الأدلة والتحقق** | سجل Evidence + جودة الدليل (§١.١٠) | عارض أدلة: كل دليل بمعياره ومراجعته الدقيقة وبيئته وإجرائه ونتيجته الخماسية ومنتجه ومراجعه ومسببات إبطاله — مع تمييز بصري للدليل الفاسد (STALE) |
| **الإصدارات والبوابات** | سجل Release + حزمة مرشح الإصدار (§١.١٠) | لكل إصدار: حزمة المرشح كاملة (فحوصات بنتائجها، خطة تراجع، مخاطر متبقية واستثناءات، اعتماد Release Authority، إيصال نشر، تحقق حي) — وREADY_FOR_APPROVAL معروضة كحالة انتظار لا إذن |
| **التسليمات** | سجل Handoff (الموسّع) | تسليمات بحالاتها السبع: من/إلى وحالة تحقق الهويتين، base/head SHA، ملفات متغيرة، اختبارات وأدلة، فحوصات لم تُشغَّل وعوائق — وما لا يجوز أن يظهر ACCEPTED وهو ناقص |
| **الحوادث** | سجل Incident (الموسّع) | حوادث بخطها الزمني المنضبط (بدأ/اكتُشف/احتُوي/حُلّ)، الخطورة، النطاق والبيانات المتأثرة بطبقات التصنيف، السبب الجذري وأفعال المتابعة |
| **السلطة والأدوار** | نموذج السلطة (§١.٢) + الأدوار (§١.٤) + قناة المالك (§١.٣) | صفحة مرجعية: جدول مصادر الحقيقة (بنسختنا بعد D-1)، الفاعلون الأربعة المنفصلون، الأدوار والمساءلات، وقاعدة «التعيين لا يمنح صلاحية» ومستويات A0–A4 مع تنبيه غياب تعريف A0/A3 |
| **التبنّي والانحرافات** | دليل التبنّي (§٤) + ملف التبنّي عندنا | خطوات التبنّي العشر بحالتها الحية عندنا، والانحرافات D-1/D-2/D-3 بمعتمِديها، وفجوات §٥ كما هي — صفحة الشفافية الحوكمية |
| **حالة التحقق الآلي** | الفاليديتوران (§٣) + خط الأنابيب عندنا | نتائج كل طبقة تحقق كما هي بحالتها الصادقة: سلامة سلسلة السجل ✓ شغالة، حارس الرباعية ✓ شغال، فاليديتورا PGOS «مُجهّز/مؤجل تنفيذيًا» حتى يُشغَّلا فعليًا — بلا أي PASS مدّعى قبل حدوثه، وبتاريخ ومراجعة دقيقة لكل نتيجة |
| **اسأل الشركة (NotebookLM)** | طبقة أسئلة فوق مستندات المقر (قرار تبنّي سابق موثق) | رابط/إرشاد لنوت بوك المقر كمكوّن مكمّل قراءة فقط — مع تنبيه PGOS الضمني: طبقة أسئلة ليست سجلًا ولا سلطة |

### ٦.٣ ما يفرضه PGOS على بيانات الموقع تحديدًا

- **نموذج البيانات = سجلات PGOS نفسها:** الأنواع التسعة في §٢ بحقولها هي مخطط بيانات الموقع؛ لا نموذج موازٍ يُخترع (وهو قرار DEC-TOTO-001 أصلًا: صيغ سجلات PGOS هي صيغ سجلنا، منقولة في JSONL بسلسلة تجزئة — D-2).
- **كل بطاقة عرض تحمل:** المعرّف الثابت، المراجعة (revision)، الحالة بمفردات PGOS، رابط المصدر الكانوني، وتاريخ آخر دليل وصلاحيته.
- **الأقسام تُبنى على دورات الحياة لا على اختراعات واجهة:** أعمدة/تبويبات أوامر الشغل والقرارات والمشاريع والإصدارات هي حالات PGOS نفسها بترتيبها، بما فيها الحالات الاستثنائية (BLOCKED/EXPIRED/REWORK…) لأن إخفاءها هو بالضبط نمط «الوقوع بصمت» الذي صُمم النظام لمنعه.
- **قسم «حالة التحقق الآلي» شرط إطلاق:** لا يُعلن الموقع جاهزًا قبل اختبار الكسر المقصود (مكوّن إلزامي بقرار المالك) ولا تُعرض نتائج فاليديشن لم تحدث.
